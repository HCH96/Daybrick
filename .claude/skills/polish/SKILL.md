# Daybrick 페이지 폴리싱

"$ARGUMENTS" 대상을 폴리싱한다. **단위는 메뉴 페이지 하나**이고, 그 페이지에 속한 하위 화면(상세 화면, 팝업, 모달, 끌기 중 모습, 빈 상태·오류 상태)까지 한 번에 맡는다.

## 기준 문서와 우선순위
1. `docs/common/ai/design/design-direction.md`: **최우선 기준.** 매번 통째로 읽는다
2. `apps/desktop/src/styles/theme.css`: 값은 이 토큰만 쓴다. 새 값이 필요하면 **페이지 작업 중이라도 바로 토큰을 추가한다** (아래 "대상과 범위"의 예외). 직접 쓴 색이나 `color-mix`로 비슷한 색을 만들어 미루지 않는다. 이름은 기존 짝(`-soft`, `-line` 등)을 따르고 쓰는 곳을 주석으로 단다
3. unslop 스킬 (`.claude/skills/unslop/`): 점검 목록과 고치는 순서만 빌려 쓴다
   - 읽는 것: `SKILL.md`의 "Run it" 이후 1~9단계·"Do not"·"Checklist", `references/signs.md`
   - 홈 벽돌 벽, 프로젝트 잔디처럼 "순간"을 새로 그릴 때만 `references/visuals.md`
   - 읽지 않는 것: `references/tokens.md`(값은 theme.css), "Story video" 부분(요청할 때만)

**둘이 다르게 말하면 design-direction.md를 따른다.** 다음은 unslop과 다르게 한다.
- unslop의 **Direction(5줄 방향 정하기)은 하지 않는다.** 문서의 "방향 한 줄", "서명", 2부 표에서 그 페이지 유형의 "순간"과 "보라 쓰는 곳"을 그대로 쓴다
- unslop의 폴리싱 모드처럼 기능, 내용, 섹션 순서는 그대로 둔다. 새 장면, 새 색, 큰 배치 변경 같은 제안은 고치지 않고 보고에만 적는다
- 문서에 없는 결정(문서의 "아직 정하지 않은 것" 포함)이 필요하면 **추측하지 않는다.** AskUserQuestion으로 묻고, 답을 문서의 해당 절과 "결정 기록" 표에 먼저 적은 뒤 작업한다

## 대상과 범위
대상 목록과 진행 상태는 `docs/common/ai/design/polish-targets.md`에 있다.
- 인자가 비어 있으면 목록에서 `진행` 항목을 먼저, 없으면 첫 `대기` 항목을 고른다
- `common`(공통 기반)이 `완료`가 아니면 다른 페이지를 시작하지 않고 그 사실을 알린다
- 범위는 목록의 "코드 범위" 열이 정한다. 그 폴더 아래의 화면이 모두 하위 화면이다
- **여러 페이지가 같이 쓰는 파일**(`components/`, `styles/`, AppLayout·Sidebar·TitleBar, 공용 Modal·Popover·ConfirmDialog·EmptyState 등)은 페이지 작업에서 고치지 않는다. 고칠 게 보이면 보고의 "공통 기반 제안"에 적는다. 페이지만 다르게 보여야 하면 그 페이지 CSS에서 덮어쓴다
  - 예외: theme.css에 **새 토큰을 추가하는 것**은 페이지 작업에서 한다. 이미 있는 토큰의 값을 바꾸거나 지우는 것만 공통 기반 몫이다
  - `color-mix`는 카테고리 색처럼 값이 실행 중에 정해지는 색을 연하게 할 때만 쓴다. 고정된 색 조합이면 토큰으로 만든다
- 다른 기능의 코드, 노트, 명세는 읽지 않는다. 기능 동작(store, reducer, api)은 건드리지 않는다

## 진행 순서

### 1. 이어서 하는지 확인
목록에서 대상이 `진행`이면 그 기능의 진행 기록 목차(아래 "기록")에서 마지막 폴리싱 기록만 읽고, 끝난 하위 화면은 건너뛴다.

### 2. 하위 화면 목록 만들기
코드 범위 폴더에서 화면을 찾는다. 컴포넌트 이름과 렌더 위치(Modal·Popover·조건부 렌더)로 판단하고, 파일을 전부 읽지 않는다. 표로 정리한다: `화면 | 여는 방법 | 주요 파일`.

### 3. 점검
- design-direction.md 1부 규칙(페이지 틀, 제목, 글씨, 크기·굵기, 색, 간격, 모서리, 부품, 문구, 움직임)과 2부의 그 유형 절에 어긋나는 곳을 찾는다
- unslop `signs.md`의 징후도 함께 찾는다
- 한 줄에 하나씩, `화면 · 어긋난 점 · 파일:줄` 형식. 같은 문제가 여러 곳에 있으면 한 줄로 묶는다
- 빠른 확인용 grep: 4배수가 아닌 px(6·10·14·18·22), `font-weight: 7|800`, `12.5px`·`13.5px`, theme.css 밖의 `#`·`rgb(`, `transition: all`, `!`, `text-transform: uppercase`, `italic`, `box-shadow`, `gradient`, 이모지

### 4. 계획 보여주고 멈추기
하위 화면 표, 점검 목록, 단계별로 고칠 내용 요약, 물어볼 결정(있으면)을 한 번에 보여주고 **승인을 기다린다.** 승인은 페이지 전체에 한 번만 받는다. 사용자가 "그냥 진행"이라고 했으면 건너뛴다.
승인되면 목록의 상태를 `진행`으로 바꾼다.

### 5. 9단계로 고치기
unslop 순서대로 고친다: **간격 → 색 → 아이콘 → 문구 → 글씨 → 배치 → 세부 → 그림 → 움직임.**
- 단계마다 본 화면과 모든 하위 화면을 함께 맞춘 뒤 다음 단계로 간다. 같은 페이지 안에서 같은 부품은 같은 값을 쓴다
- "그림" 단계는 2부 표의 "순간"이 있는 페이지만 한다. 순간이 "없음"이면 건너뛴다
- 하위 화면이 많아 한 번에 끝나지 않으면 하위 화면 단위로 끊는다. 끊을 때는 기록에 끝난 하위 화면과 남은 것을 적는다

### 6. 확인
- `apps/desktop`에서 `npm run build`(타입 검사 포함)가 성공해야 한다
- 브라우저 미리보기(`.claude/launch.json`의 `desktop-web`)로 본 화면과 주요 하위 화면을 열어 스크린샷으로 확인한다. 화면 확인은 최대 3번 정도로 끝낸다. 미리보기에서 열리지 않는 화면은 코드로만 확인했다고 보고한다
- unslop "Checklist"와 3단계 점검 목록을 다시 대조해 남은 것을 고친다

### 7. 기록과 마무리
- **기록**: `docs/common/ai/formats/record-format.md` 양식으로 진행 기록을 남긴다. 위치는 목록의 "기록 위치" 열. 종류는 `수정`, 요구사항은 `폴리싱`. 문서 규칙에 따른 결정은 design-direction.md에 이미 적었으므로 decisions.md에는 올리지 않는다
- **목록**: 대상 상태를 `완료`로 바꾸고 날짜를 적는다. 하위 화면이 남아 끊었으면 `진행`을 유지한다
- **목업 표시**: 그 기능에 `human/mockups/index.html`이 있으면 목차 주석 첫 줄 바로 아래에 `.claude/commands/mockup.md`의 "폴리싱 표시" 줄을 넣는다 (이미 있으면 날짜만 고친다). 목업 파일은 고치거나 옮기지 않는다. common은 특정 목업이 없으므로 넣지 않는다
- PROJECT.md의 기능 상태는 바꾸지 않는다 (폴리싱은 기능 상태와 따로 관리한다)
- 바꾼 코드와 문서를 함께 커밋한다. 메시지: `<페이지 이름> 폴리싱: <요약>`

### 8. 보고

- 단계별로 바뀐 점 몇 줄
- 실제로 실행·확인한 것과 코드만 보고 판단한 것을 나눠서
- 이번에 design-direction.md에 새로 적은 결정
