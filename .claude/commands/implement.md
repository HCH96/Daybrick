"$ARGUMENTS" 기능을 구현할 거야. 기능 폴더는 docs/features/<기능명>/ 이다 (아래 경로는 모두 이 폴더 기준).
- 그 폴더가 없으면 `ls docs/features/`로 폴더 이름만 확인해 맞는 폴더를 쓴다 (대소문자·단수형 차이). 폴더 안 전체 목록(ls -R)은 보지 않는다.

## 진행 관리 (메인 세션)
메인 세션은 코드를 읽거나 고치지 않고, 단계마다 **새 하위 에이전트**(Agent, `subagent_type: implement-step`)를 띄워 맡긴다. 이 에이전트는 `.claude/agents/implement-step.md`에 정의돼 있고 단계 작업에 쓰는 도구만 갖는다 (없으면 general-purpose로 대신한다). 앞 단계의 문맥이 다음 단계에 쌓이지 않게 하려는 것이다. 단계 사이의 인계는 노트(notes.md)와 git 커밋으로만 한다.

1. notes.md의 "다음 진행"과 ai/plan/index.md의 단계 표에서 남은 단계를 확인한다. 노트가 없으면 ai/logs/index.md 목차로 다음 단계를 정한다. 계획 문서가 없으면 멈추고 알려준다.
2. 남은 단계마다 차례로 하위 에이전트를 하나씩 띄운다 (동시에 여러 개 띄우지 않는다). 넘길 지시:
   "`.claude/commands/implement.md`의 '한 단계 하는 법'을 읽고, <기능명> 기능의 N단계를 그대로 끝까지(커밋까지) 해줘. 끝나면 '돌려줄 결과' 양식으로만 답해줘."
3. 결과를 받으면 `git log -1 --oneline`과 notes.md의 "다음 진행" 첫 줄만 보고 커밋·노트가 실제로 갱신됐는지 확인한다.
4. 결과가 "멈춤"이거나 확인이 어긋나면 다음 단계로 가지 않고 이유를 사용자에게 알리고 기다린다.
5. 단계 사이에는 사용자에게 보고하지 않는다.

모든 단계가 끝나면 (메인이 직접):
- PROJECT.md의 기능별 상태와 기능 허브의 상태 줄을 "구현 완료 (테스트 대기)"로 바꾼다 (상태 줄만 grep으로 찾아 고침).
- 작업 노트의 "다음 진행"을 `/test <기능명>` 한 줄로 바꾸고 "확인할 문서"는 비운다.
- 토큰 보고서: 프로젝트 루트에서 `node .claude/scripts/token-report.mjs --title "<기능명> /implement" --out docs/common/ai/token-reports/<기능명>-<YYYY-MM-DD>.md`를 실행한다. 보고서 파일은 읽지 않고, 콘솔에 나온 3줄로 docs/common/ai/token-reports/index.md 표에 한 줄 추가한다.
- 위 변경을 함께 커밋한다.
- 그때 한 번만 보고한다: 단계별 커밋 목록, 자동 판단으로 계획과 달라진 점, 토큰 보고서 경로와 총 입력·최대 컨텍스트, `/test <기능명>`으로 이어가라는 안내.
- 중간에 "멈춤"으로 끝날 때도 위 토큰 보고서 명령을 실행해 경로를 함께 알린다 (커밋은 하지 않는다).

## 한 단계 하는 법 (하위 에이전트)
먼저 작업 노트 notes.md와 ai/logs/index.md(목차) 두 파일만 읽는다. 노트가 없다는 걸 확인하기 전에는 ai/plan/index.md를 읽지 않는다.
- 노트가 있으면: "확인할 문서"에 적힌 파일만 읽고, 지시받은 단계(= "다음 진행" 첫 줄)를 한다.
  - "관련 결정"에 적힌 D 번호는 ai/spec/decisions.md에서 그 줄만 찾아 읽는다.
  - 노트의 "완료"와 ai/logs/index.md(기록 목차)가 서로 다르면 구현하지 말고 "멈춤"으로 돌려준다. (기록 항목 파일은 읽지 않고 목차만 비교)
- 노트가 없으면: ai/plan/index.md → 그 단계의 ai/plan/step-NN.md → step 파일에 적힌 요구사항(R)이 든 ai/spec/req-<묶음>.md (ai/spec/index.md의 묶음 표로 찾기) 순서로 읽는다.

확인할 문서 읽는 법:
- 파일은 통째로 읽되, 적힌 파일 말고 같은 폴더의 다른 파일을 훑어 읽지 않는다.
- 목업: step 파일이나 노트에 적힌 화면 파일만 읽는다. CSS는 노트에 적힌 CSS 파일(없으면 화면 파일 머리에 적힌 파일)에서, 그 구역에 실제로 쓰인 클래스 이름을 그대로 검색한다. `.sub`, `.opt`처럼 짧은 앞부분으로 넓게 검색하지 않는다. icons.js는 아이콘 모양이 필요할 때만 id로 검색한다.
- 진행 기록: ai/logs/index.md에서 필요한 항목을 고르고 그 LNN.md만 읽는다.
- 전체 파일 목록·컴포넌트 구조가 꼭 필요할 때만 ai/plan/structure.md를 읽는다.
- 목록 밖 문서가 꼭 필요해지면 필요한 줄만 grep으로 읽는다. 그리고 노트를 쓸 때 다음 단계 "확인할 문서"에 그 파일을 미리 적는다.

코드 읽는 법:
- 이번 단계에서 고칠 파일만 통째로 읽는다. 가져다 쓰기만 하는 파일(공용 컴포넌트, 유틸, CSS)은 export·props·클래스 이름만 grep으로 본다.
- 고칠 파일은 Read 도구로 읽는다. Bash의 cat으로 읽으면 Edit 전에 다시 읽어야 한다.

계획과 다르게 해야 할 때:
- 파일 위치·이름·내부 구조처럼 사용자가 보는 동작이 안 바뀌는 차이: 결정(D)으로 올리고, 기록의 "계획과 달라진 점"에 "(자동 진행 중 판단)"으로 적고 진행한다.
- 요구사항이나 화면 동작이 바뀌는 차이: 구현하지 말고 "멈춤"으로 돌려준다.

구현을 마치면 순서대로:
1. 확인: apps/desktop에서 `npm run build`(타입 검사 포함), Rust를 고쳤으면 src-tauri에서 `cargo check`. 실패하면 고친다. 고치지 못하면 커밋하지 않고 "멈춤"으로 돌려준다.
2. 진행 기록 항목을 남긴다 (아래 "진행 기록 쓰는 법"). 사용자 확인 칸은 "대기 (최종 테스트)". 계획 문서에 없는 확인거리가 생겼으면 "테스트 메모" 줄을 적는다.
3. 이번 단계에서 생긴 결정이 있으면 ai/spec/decisions.md에 올린다 (아래 "결정 올리기").
4. 작업 노트를 갱신한다 (아래 "노트 쓰는 법").
5. 기능 허브(index.md)의 상태 줄과 PROJECT.md의 기능별 상태를 "구현 중 (N/전체 단계 완료)"로 갱신한다. 둘 다 상태 줄만 grep으로 찾아 고친다.
6. 이번 단계의 코드와 문서만 커밋한다. 메시지: `<기능 이름> N단계: <단계 이름> (R..–R..)`. push는 하지 않는다.
- 진행 기록·노트는 이 파일의 양식대로 쓴다. 형식을 보려고 예전 기록 파일(LNN.md)을 읽지 않는다.

돌려줄 결과 (이 양식만, 5줄 이내):
```
결과: 완료 / 멈춤
커밋: <해시> <메시지> (멈춤이면 "없음")
자동 판단: <계획과 달라진 점 한 줄, 없으면 "없음">
멈춘 이유: <멈춤일 때만>
```

## 노트 쓰는 법
노트는 다음 단계의 하위 에이전트에게 "무엇을 하고, 어떤 파일만 읽으면 되는지"를 알려 주는 유일한 인계 문서다. 지난 일의 자세한 내용은 진행 기록에 둔다.

파일: docs/features/<기능명>/notes.md (기능당 하나). 첫 단계를 마칠 때 만들고, 기능 허브(index.md)에 링크한다.

```markdown
# <기능 이름> (<기능명>) 작업 노트
갱신: YYYY-MM-DD

## 완료
- 4단계: <계획의 단계 이름> (사용자 확인 완료)
- 5단계: <계획의 단계 이름> (자동 진행, 최종 테스트 대기)

## 다음 진행
- 6단계: <계획의 단계 이름> (<무엇을 하는지 한 줄>)
- 관련 결정: D1, D3, D4 (ai/spec/decisions.md에서 이 줄만 읽기)
- 주의: <결정이 아닌, 이 단계에만 필요한 세부 사항>

## 확인할 문서 (경로는 docs/features/<기능명>/ 기준, 파일 통째로 읽기)
- ai/plan/step-06.md
- ai/spec/req-status.md
- ai/logs/L07.md
- human/mockups/part-status.html, part-result.html (CSS: parts.css·common.css에서 클래스 검색)
- ai/plan/structure.md의 status/ 줄 (새 파일 위치를 정할 때만)
```

규칙:
- 세 칸("완료 / 다음 진행 / 확인할 문서")만 쓰고 30줄을 넘기지 않는다.
- 완료: 계획의 단계 이름 그대로, 단계마다 한 줄. 확인 상태를 괄호로 적는다. 자세한 내용은 쓰지 않는다 (진행 기록에 있다).
- 다음 진행:
  - 첫 줄은 다음 단계 번호와 이름.
  - "관련 결정"은 decisions.md 전체를 보고, 적용 범위에 다음 단계가 들어가는 결정을 빠짐없이 적는다. 없으면 "관련 결정: 없음".
  - "주의"는 결정(D)으로 올릴 만큼 오래가지 않는, 다음 단계에만 필요한 세부 사항에만 쓴다. 다음 단계보다 오래 지켜야 하면 결정으로 올린다.
- 확인할 문서: 읽을 **파일 경로**를 적는다. 폴더나 색인만 적지 않는다. 한 화면 파일 안의 일부만 필요하면 구역 ID를 덧붙인다 (예: popup.html의 popup-status 구역).
  - 기본: 다음 단계의 step 파일, 그 단계 R이 든 req 파일, 직전 단계 기록 파일, step 파일에 적힌 목업 화면 파일.
  - 목업을 적을 때는 클래스를 검색할 CSS 파일을 괄호로 함께 적는다. 새 파일을 만드는 단계면 structure.md에서 볼 구역을 적는다.
- 노트를 고칠 때마다 "갱신" 날짜를 바꾼다.
- 마지막 단계를 마친 하위 에이전트는 "다음 진행"을 비워 두지 말고 "모든 단계 완료"로 적는다. `/test` 안내는 메인이 바꾼다.

## 진행 기록 쓰는 법
명령 없이 하는 작업에서 기록을 남길 때도 이 형식을 따른다.

폴더: docs/features/<기능명>/ai/logs/
- index.md: 기록 목차 하나. 항목을 추가하면 같은 작업에서 한 줄 추가한다.
- LNN.md: 기록 항목 하나당 파일 하나 (L01.md, L02.md …).

index.md:
```markdown
# <기능 이름> (<기능명>) 진행 기록 목차
항목 하나당 파일 하나(`L번호.md`). 필요한 항목 파일만 읽는다.

| ID | 날짜 | 종류 | 요구사항 | 내용 |
|---|---|---|---|---|
| [L08](L08.md) | 2026-10-23 | 구현 | R17–R22 | 5단계: 상태 (최종 테스트 대기) |
```

LNN.md:
```markdown
# L08 · 2026-10-23 · 구현 5단계: 상태

- 요구사항: R17–R22
- 한 일: (3~6줄)
- 결정: D6 추가 (있을 때만)
- 계획과 달라진 점: (있을 때만, "(자동 진행 중 판단)" 또는 사용자 승인 여부 포함)
- 확인: 빌드·타입 검사 결과 (1~3줄, 실제로 실행한 것만)
- 사용자 확인: 완료 / 대기 (최종 테스트)
- 테스트 메모: (있을 때만, 1~2줄)
- 남은 문제: (있을 때만)
- 주요 파일: 핵심 파일 몇 개만
```

- 종류: 명세 / 목업 / 계획 / 구현 / 테스트 / 수정
- ID: 기능 안에서 L01부터 차례로 붙인다. 한 번 붙인 번호는 바꾸지 않는다. (보관 폴더로 옮긴 옛 기록이 있으면 그 다음 번호부터 이어 간다.)
- 요구사항: R 번호. 기능 전체에 걸친 항목은 "전체".
- 테스트 메모: 테스트 항목은 /test가 명세서와 step 파일의 "확인할 결과"로 한 번에 만든다. 여기에는 문서만 봐서는 알 수 없는 확인거리만 적는다 (예: "긴 제목은 말줄임 처리 → 30자 넘는 제목 확인", "일정 없는 달은 빈 칸"). 계획대로라 더할 게 없으면 줄을 쓰지 않는다.
- 항목 본문은 30줄 이내로 쓴다. 파일마다 넣은 함수·CSS 값 같은 세부 목록, 계획 문서에 이미 있는 내용의 반복("step-05대로"로 충분)은 쓰지 않는다. 앞으로 지킬 내용은 결정으로 decisions.md에 올린다.

## 결정 올리기
앞으로의 작업에서도 지켜야 할 결정(구조, 규칙, 계획과 달라진 방식, 개발 환경 주의점 등)은 기록에만 두지 않는다.

- ai/spec/decisions.md에 번호를 붙여 올린다:
  `- D6. 내용 (적용: 5~7단계 / 이후 전체) (기록: L08)`
- 적용 범위는 계획 색인(ai/plan/index.md)의 단계 표를 보고 정한다. 확실하지 않으면 "이후 전체"로 적는다.
- 결정이 바뀌면 지우지 않고 줄을 고친 뒤 끝에 "(L번호에서 변경)"을 붙인다.
- 기록 항목의 "결정" 줄에 D 번호를 적어 서로 이어지게 한다.
