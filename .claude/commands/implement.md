"$ARGUMENTS" 기능을 구현할 거야. 기능 폴더는 docs/features/<기능명>/ 이다 (아래 경로는 모두 이 폴더 기준).

먼저 작업 노트 notes.md를 읽어줘.
- 노트가 있으면: "확인할 문서"에 적힌 파일만 읽고, "다음 진행"에 적힌 단계를 시작해줘.
  - "관련 결정"에 적힌 D 번호는 ai/spec/decisions.md에서 그 줄만 찾아 읽어줘.
  - 노트의 "완료"와 ai/logs/index.md(기록 목차)가 서로 다르면 구현하지 말고 나에게 물어봐줘. (기록 항목 파일은 읽지 않고 목차만 비교)
- 노트가 없으면: 아래 순서로 필요한 파일만 읽고 첫 단계(또는 기록 목차상 다음 단계)부터 시작해줘.
  - ai/plan/index.md → 시작할 단계의 ai/plan/step-NN.md
  - step 파일에 적힌 요구사항(R)이 든 ai/spec/req-<묶음>.md (ai/spec/index.md의 묶음 표로 찾기)
  - ai/logs/index.md (목차만)

계획 문서(ai/plan/index.md)를 찾지 못하면 구현하지 말고 나에게 알려줘.

확인할 문서 읽는 법:
- 파일은 통째로 읽되, 적힌 파일 말고 같은 폴더의 다른 파일을 훑어 읽지 않는다.
- 목업: step 파일이나 노트에 적힌 화면 파일만 읽는다. CSS는 화면 파일 머리에 적힌 CSS 파일에서 그 화면이 쓰는 클래스만 검색해서 읽는다. icons.js는 아이콘 모양이 필요할 때만 id로 검색한다.
- 진행 기록: ai/logs/index.md에서 필요한 항목을 고르고 그 LNN.md만 읽는다.
- 전체 파일 목록·컴포넌트 구조가 꼭 필요할 때만 ai/plan/structure.md를 읽는다.

구현 방식:
- 이 세션에서는 계획의 단계 하나만 구현해줘.
- 단계가 끝나면 무엇을 했는지와 내가 확인할 결과를 알려줘.
- 계획과 다르게 해야 할 이유가 생기면 바로 바꾸지 말고 먼저 나에게 물어봐줘.

내가 단계 결과를 확인하면:
1. 진행 기록 항목을 남겨줘 (아래 "진행 기록 쓰는 법").
2. 이번 단계에서 생긴 결정이 있으면 ai/spec/decisions.md에 올려줘 (아래 "결정 올리기").
3. 작업 노트를 갱신해줘 (아래 "노트 쓰는 법").
4. 기능 허브(index.md)의 상태 줄과 PROJECT.md의 기능별 상태를 "구현 중 (N/전체 단계 완료)"로 갱신해줘.
5. 다음 단계로 넘어가지 말고, 새 세션에서 /implement $ARGUMENTS 로 이어가라고 알려줘.

모든 단계가 끝나면:
- PROJECT.md의 기능별 상태와 기능 허브의 상태 줄을 갱신해줘.
- 작업 노트의 "다음 진행"에 /test $ARGUMENTS 를 적어줘.
- /test $ARGUMENTS 로 테스트를 진행하라고 알려줘.

## 노트 쓰는 법
노트는 다음 세션이 "무엇을 하고, 어떤 파일만 읽으면 되는지"를 알려 주는 문서다. 지난 일의 자세한 내용은 진행 기록에 둔다.

파일: docs/features/<기능명>/notes.md (기능당 하나). 첫 단계를 마치고 사용자가 확인했을 때 만들고, 기능 허브(index.md)에 링크한다.

```markdown
# <기능 이름> (<기능명>) 작업 노트
갱신: YYYY-MM-DD

## 완료
- 1단계: <계획의 단계 이름> (사용자 확인 완료)

## 다음 진행
- 5단계: <계획의 단계 이름> (<무엇을 하는지 한 줄>)
- 관련 결정: D1, D3, D4 (ai/spec/decisions.md에서 이 줄만 읽기)
- 주의: <결정이 아닌, 이 단계에만 필요한 세부 사항>

## 확인할 문서 (경로는 docs/features/<기능명>/ 기준, 파일 통째로 읽기)
- ai/plan/step-05.md
- ai/spec/req-status.md
- ai/logs/L07.md
- human/mockups/part-status.html, part-result.html
```

규칙:
- 세 칸("완료 / 다음 진행 / 확인할 문서")만 쓰고 30줄을 넘기지 않는다.
- 완료: 계획의 단계 이름 그대로, 단계마다 한 줄. 사용자 확인 여부를 괄호로 적는다. 자세한 내용은 쓰지 않는다 (진행 기록에 있다).
- 다음 진행:
  - 첫 줄은 다음 단계 번호와 이름.
  - "관련 결정"은 decisions.md 전체를 보고, 적용 범위에 다음 단계가 들어가는 결정을 빠짐없이 적는다. 없으면 "관련 결정: 없음".
  - "주의"는 결정(D)으로 올릴 만큼 오래가지 않는, 다음 단계에만 필요한 세부 사항(예: 특정 컴포넌트의 위치 값)에만 쓴다. 다음 단계보다 오래 지켜야 하면 주의가 아니라 결정으로 올린다.
- 확인할 문서: 읽을 **파일 경로**를 적는다. 폴더나 색인만 적지 않는다. 한 화면 파일 안의 일부만 필요하면 구역 ID를 덧붙인다 (예: popup.html의 popup-status 구역).
  - 기본: 다음 단계의 step 파일, 그 단계 R이 든 req 파일, 직전 단계 기록 파일, step 파일에 적힌 목업 화면 파일.
- 노트를 고칠 때마다 "갱신" 날짜를 바꾼다.
- 모든 단계가 끝나면 "다음 진행"을 `/test <기능명>` 한 줄로 바꾸고, "확인할 문서"는 비운다.

## 진행 기록 쓰는 법
명령 없이 하는 작업에서 기록을 남길 때도 이 형식을 따른다.

폴더: docs/features/<기능명>/ai/logs/
- index.md: 기록 목차 하나. 항목을 추가하면 같은 작업에서 한 줄 추가한다.
- LNN.md: 기록 항목 하나당 파일 하나 (L01.md, L02.md …). 파일이 길어져 다음 파일로 넘어가는 규칙은 없다.

index.md:
```markdown
# <기능 이름> (<기능명>) 진행 기록 목차
항목 하나당 파일 하나(`L번호.md`). 필요한 항목 파일만 읽는다.

| ID | 날짜 | 종류 | 요구사항 | 내용 |
|---|---|---|---|---|
| [L08](L08.md) | 2026-10-23 | 구현 | R17–R22 | 5단계: 상태 (사용자 확인) |
```

LNN.md:
```markdown
# L08 · 2026-10-23 · 구현 5단계: 상태

- 요구사항: R17–R22
- 한 일: (3~6줄)
- 결정: D6 추가 (있을 때만)
- 계획과 달라진 점: (있을 때만, 사용자 승인 여부 포함)
- 확인: 빌드·타입 검사·화면 확인 결과 (1~3줄)
- 사용자 확인: 완료 / 대기
- 남은 문제: (있을 때만)
- 주요 파일: 핵심 파일 몇 개만
```

- 종류: 명세 / 목업 / 계획 / 구현 / 테스트 / 수정
- ID: 기능 안에서 L01부터 차례로 붙인다. 한 번 붙인 번호는 바꾸지 않는다. (보관 폴더로 옮긴 옛 기록이 있으면 그 다음 번호부터 이어 간다.)
- 요구사항: R 번호. 기능 전체에 걸친 항목은 "전체".
- 항목 본문은 30줄 이내로 쓴다. 쓰지 않는 것:
  - 파일마다 넣은 함수·CSS 값 같은 세부 목록 (코드가 기준이다)
  - 계획 문서에 이미 있는 내용의 반복 ("step-05대로"로 충분)
  - 30줄을 넘을 것 같으면, 앞으로 지킬 내용은 결정으로 decisions.md에 올리고 단계 설계는 step 파일에 둔다.

## 결정 올리기
앞으로의 작업에서도 지켜야 할 결정(구조, 규칙, 계획과 달라진 방식, 개발 환경 주의점 등)은 기록에만 두지 않는다.

- ai/spec/decisions.md에 번호를 붙여 올린다:
  `- D6. 내용 (적용: 5~7단계 / 이후 전체) (기록: L08)`
- 적용 범위는 계획 색인(ai/plan/index.md)의 단계 표를 보고 정한다. 확실하지 않으면 "이후 전체"로 적는다.
- 결정이 바뀌면 지우지 않고 줄을 고친 뒤 끝에 "(L번호에서 변경)"을 붙인다.
- 기록 항목의 "결정" 줄에 D 번호를 적어 서로 이어지게 한다.
