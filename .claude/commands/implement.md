"$ARGUMENTS" 기능을 구현할 거야.

먼저 docs/ai/notes 아래의 "$ARGUMENTS" 작업 노트(<기능명>-notes.md)를 찾아 읽어줘.
- 노트가 있으면: "확인할 문서"에 적힌 문서만 읽고, "다음 진행"에 적힌 단계를 시작해줘.
  - "관련 결정"에 적힌 D 번호는 명세서 결정 사항에서 그 줄만 찾아 읽어줘.
  - 노트의 "완료"와 진행 기록 목차가 서로 다르면 구현하지 말고 나에게 물어봐줘. (기록 본문은 읽지 않고 목차만 비교)
- 노트가 없으면: 아래 문서를 읽고 첫 단계(또는 진행 기록 목차상 다음 단계)부터 시작해줘.
  - docs/ai/features 아래의 "$ARGUMENTS" 기능 명세서
  - docs/ai/plans 아래의 "$ARGUMENTS" 계획 문서
  - docs/ai/logs 아래의 "$ARGUMENTS" 최신 기록 파일의 목차

계획 문서를 찾지 못하면 구현하지 말고 나에게 알려줘.

확인할 문서 읽는 법:
- 목업: 맨 앞 목업 목차만 읽고, 필요한 ID 구역만 검색해서 읽는다. CSS는 그 구역에서 쓰는 클래스만 검색해서 읽는다.
- 진행 기록: 맨 앞 기록 목차만 읽고, 필요한 항목(`## L번호`)만 검색해서 읽는다.
- 명세서·계획: 노트에 범위(R 번호, 절 이름, 계획 절 번호)가 적혀 있으면 그 부분만 읽는다.

구현 방식:
- 이 세션에서는 계획의 단계 하나만 구현해줘.
- 단계가 끝나면 무엇을 했는지와 내가 확인할 결과를 알려줘.
- 계획과 다르게 해야 할 이유가 생기면 바로 바꾸지 말고 먼저 나에게 물어봐줘.

내가 단계 결과를 확인하면:
1. 진행 기록 파일에 항목을 남겨줘 (아래 "진행 기록 쓰는 법").
2. 이번 단계에서 생긴 결정이 있으면 명세서 결정 사항에 올려줘 (아래 "결정 올리기").
3. 작업 노트를 갱신해줘 (아래 "노트 쓰는 법").
4. 다음 단계로 넘어가지 말고, 새 세션에서 /implement $ARGUMENTS 로 이어가라고 알려줘.

모든 단계가 끝나면:
- PROJECT.md의 기능별 상태를 갱신해줘.
- 작업 노트의 "다음 진행"에 /test $ARGUMENTS 를 적어줘.
- /test $ARGUMENTS 로 테스트를 진행하라고 알려줘.

## 노트 쓰는 법
노트는 다음 세션이 "무엇을 하고, 무엇만 읽으면 되는지"를 알려 주는 문서다. 지난 일의 자세한 내용은 진행 기록에 둔다.

파일: docs/ai/notes/<기능명>-notes.md (기능당 하나). 첫 단계를 마치고 사용자가 확인했을 때 만들고, DOCS_INDEX.md에 추가한다.

```markdown
# <기능 이름> (<기능명>) 작업 노트
갱신: YYYY-MM-DD

## 완료
- 1단계: <계획의 단계 이름> (사용자 확인 완료)

## 다음 진행
- 5단계: <계획의 단계 이름> (<무엇을 하는지 한 줄>)
- 관련 결정: D1, D3, D4 (명세서 "결정 사항"에서 이 줄만 읽기)
- 주의: <결정이 아닌, 이 단계에만 필요한 세부 사항>

## 확인할 문서
- docs/ai/features/<기능명>.md (R17–R22, R33)
- docs/ai/plans/<기능명>-plan.md (0절, 3절 5단계)
- docs/ai/logs/<기능명>-log.md (기록 목차 + L07)
- docs/human/mockups/<기능명>.html#parts-status, #parts-result
```

규칙:
- 세 칸("완료 / 다음 진행 / 확인할 문서")만 쓰고 30줄을 넘기지 않는다.
- 완료: 계획의 단계 이름 그대로, 단계마다 한 줄. 사용자 확인 여부를 괄호로 적는다. 자세한 내용은 쓰지 않는다 (진행 기록에 있다).
- 다음 진행:
  - 첫 줄은 다음 단계 번호와 이름.
  - "관련 결정"은 명세서 결정 사항 전체를 보고, 적용 범위에 다음 단계가 들어가는 결정을 빠짐없이 적는다. 없으면 "관련 결정: 없음".
  - "주의"는 결정(D)으로 올릴 만큼 오래가지 않는, 다음 단계에만 필요한 세부 사항(예: 특정 컴포넌트의 위치 값)에만 쓴다. 다음 단계보다 오래 지켜야 하면 주의가 아니라 결정으로 올린다.
- 확인할 문서: 문서마다 읽을 범위를 함께 적는다 (R 번호, 계획 절, 기록 L번호, 목업 ID). 범위 없이 문서 이름만 적지 않는다.
- 노트를 고칠 때마다 "갱신" 날짜를 바꾼다.
- 모든 단계가 끝나면 "다음 진행"을 `/test <기능명>` 한 줄로 바꾸고, "확인할 문서"는 비운다.

## 진행 기록 쓰는 법
명령 없이 하는 작업에서 기록을 남길 때도 이 형식을 따른다.

파일: docs/ai/logs/<기능명>-log.md (이어 쓴 파일은 -log-2.md, -log-3.md …). 항상 가장 최신 파일에 쓴다.

파일 구성:
```markdown
# <기능 이름> 진행 기록
- 담은 범위: L01~L13 (명세 ~ 1차 테스트)
- 이전 파일: 없음 / 다음 파일: <기능명>-log-2.md

## 기록 목차
| ID | 날짜 | 종류 | 요구사항 | 내용 |
|---|---|---|---|---|
| L08 | 2026-10-23 | 구현 | R17–R22 | 5단계: 상태 (사용자 확인) |

## L08 · 2026-10-23 · 구현 5단계: 상태
- 요구사항: R17–R22
- 한 일: (3~6줄)
- 결정: D6 추가 (있을 때만)
- 계획과 달라진 점: (있을 때만, 사용자 승인 여부 포함)
- 확인: 빌드·타입 검사·화면 확인 결과 (1~3줄)
- 사용자 확인: 완료 / 대기
- 남은 문제: (있을 때만)
- 주요 파일: 핵심 파일 몇 개만
```

- 종류: 명세 / 목업 / 계획 / 구현 / 테스트 / 수정
- ID: 기능 안에서 L01부터 차례로 붙이고, 파일이 바뀌어도 번호를 이어 간다. 한 번 붙인 번호는 바꾸지 않는다.
- 요구사항: R 번호. 기능 전체에 걸친 항목은 "전체".
- 항목을 추가하면 목차에도 같은 작업에서 한 줄 추가한다.
- 항목 본문은 30줄 이내로 쓴다. 쓰지 않는 것:
  - 파일마다 넣은 함수·CSS 값 같은 세부 목록 (코드가 기준이다)
  - 계획 문서에 이미 있는 내용의 반복 ("계획 3절대로"로 충분)
  - 30줄을 넘을 것 같으면, 앞으로 지킬 내용은 결정으로 명세서에 올리고 단계 설계는 계획 문서에 둔다.

새 파일로 넘어가는 때:
- 이전 작업 묶음(목업·계획 → 단계 구현 → 테스트)이 테스트까지 끝난 뒤, 새 목업이나 새 계획 문서로 시작하는 작업이 생기면 새 파일을 만든다.
  (테스트 뒤의 작은 수정처럼 새 계획 없이 하는 일은 지금 파일에 이어 쓴다.)
- 위와 상관없이 파일이 1,000줄을 넘으면 새 파일을 만든다.
- 새 파일을 만들면 앞 파일 머리의 "다음 파일"과 "담은 범위"를 고치고, DOCS_INDEX.md와 노트의 기록 파일 경로를 새 파일로 바꾼다.

## 결정 올리기
앞으로의 작업에서도 지켜야 할 결정(구조, 규칙, 계획과 달라진 방식, 개발 환경 주의점 등)은 기록에만 두지 않는다.

- 명세서 "결정 사항"에 번호를 붙여 올린다:
  `- D6. 내용 (적용: 5~7단계 / 이후 전체) (기록: L08)`
- 적용 범위는 계획 문서를 보고 정한다. 확실하지 않으면 "이후 전체"로 적는다.
- 결정이 바뀌면 지우지 않고 줄을 고친 뒤 끝에 "(L번호에서 변경)"을 붙인다.
- 기록 항목의 "결정" 줄에 D 번호를 적어 서로 이어지게 한다.
