"$ARGUMENTS" 기능을 구현할 거야. 기능 폴더는 docs/<플랫폼>/features/<기능명>/ 이다 (아래 경로는 모두 이 폴더 기준).
- <플랫폼>은 desktop·android·web 중 하나다. 인자에 플랫폼이 없으면 `ls docs/*/features/`로 폴더 이름만 확인해 맞는 폴더를 쓴다 (대소문자·단수형 차이). 두 플랫폼에 같은 이름이 있으면 사용자에게 묻는다. 폴더 안 전체 목록(ls -R)은 보지 않는다.

## 진행 관리 (메인 세션)
메인 세션은 코드를 읽거나 고치지 않고, 단계마다 **새 하위 에이전트**(Agent, `subagent_type: implement-step`)를 띄워 맡긴다. 단계 작업 절차는 그 에이전트 정의(`.claude/agents/implement-step.md`)에 들어 있으므로 메인은 읽지 않는다. 앞 단계의 문맥이 다음 단계에 쌓이지 않게 하려는 것이다. 단계 사이의 인계는 노트(notes.md)와 git 커밋으로만 한다.

1. notes.md의 "다음 진행"과 ai/plan/index.md의 단계 표에서 남은 단계를 확인한다. 노트가 없으면 ai/logs/index.md 목차로 다음 단계를 정한다. 계획 문서가 없으면 멈추고 알려준다.
   - ai/plan/index.md 맨 위가 "종류: 수정 계획"이면 수정 회차다. 노트 "다음 진행"에 `수정 계획:` 줄이 없으면 하위 에이전트를 띄우지 말고 멈춘다 (/plan이 노트를 새로 쓰지 않은 것).
2. 남은 단계마다 차례로 하위 에이전트를 하나씩 띄운다 (동시에 여러 개 띄우지 않는다). 넘길 지시: "<기능명> 기능의 N단계를 해줘."
   - implement-step 에이전트가 없으면 general-purpose로 띄우고 지시 앞에 "`.claude/agents/implement-step.md`를 읽고 그대로 따라서"를 붙인다.
3. 결과를 받으면 `git log -1 --oneline`과 notes.md의 "다음 진행" 첫 줄만 보고 커밋·노트가 실제로 갱신됐는지 확인한다.
4. 결과가 "멈춤"이거나 확인이 어긋나면 다음 단계로 가지 않고 이유를 사용자에게 알리고 기다린다.
5. 단계 사이에는 사용자에게 보고하지 않는다.

## 모든 단계가 끝나면 (메인이 직접)
- PROJECT.md의 기능별 상태와 기능 허브의 상태 줄을 "구현 완료 (테스트 대기)"로 바꾼다 (수정 회차면 "수정 구현 완료 (테스트 대기)"). 상태 줄만 grep으로 찾아 고친다.
- 작업 노트의 "다음 진행"을 `/test <기능명>` 한 줄로 바꾸고 "확인할 문서"는 비운다.
- 위 변경을 함께 커밋한다.
- 그때 한 번만 보고한다: 단계별 커밋 목록, 자동 판단으로 계획과 달라진 점, `/test <기능명>`으로 이어가라는 안내.
