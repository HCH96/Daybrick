아래는 내가 자유롭게 말한 기능 요구사항이야.

$ARGUMENTS

이걸 바탕으로 기능 명세서를 만들어줘.

진행 방식:
0. 어느 플랫폼(desktop·android·web)의 기능인지 정한다. 요구사항에서 분명하지 않으면 먼저 묻는다. 여러 앱이 주고받는 약속(Supabase 테이블, 실시간 메시지 형식, 상태 값)은 기능 폴더가 아니라 docs/common/ai/contracts/에 따로 적는다.
1. 먼저 요구사항을 정리해서 보여주고, 빠졌거나 모호한 부분을 질문해줘. 질문은 한 번에 너무 많지 않게, 중요한 것부터 해줘.
2. 내가 정해야 하는 건 네가 마음대로 정하지 말고 질문해줘. 단순한 건 추천안을 함께 보여줘도 돼.
3. 질문이 끝나면 아래 "명세서 양식"대로 초안을 보여줘. (초안은 한 문서로 보여주고, 저장할 때 파일로 나눈다)

내가 초안을 승인하면:
- docs/<플랫폼>/features/<기능명>/ai/spec/ 아래에 "명세서 양식"의 파일들로 나눠 저장
- 기능 허브 docs/<플랫폼>/features/<기능명>/index.md를 만들기 (아래 "기능 허브 양식")
- 진행 기록 docs/<플랫폼>/features/<기능명>/ai/logs/index.md와 L01.md "명세" 항목을 남기기 (docs/common/ai/formats/record-format.md의 "진행 기록 쓰는 법")
- PROJECT.md의 기능별 상태 표에 플랫폼과 기능 허브 경로를 기록
- 플랫폼 색인 docs/<플랫폼>/index.md의 기능 허브 목록에 경로와 한 줄 설명을 추가 (DOCS_INDEX.md는 고치지 않는다)

이미 있는 기능의 명세서를 고칠 때는 ai/spec/index.md에서 고칠 파일만 찾아 읽고, ai/logs/index.md(목차)를 확인한 뒤, 아래 "R 번호 규칙"을 지켜 고치고 고친 내용을 "명세" 항목으로 남겨줘.

아직 코드는 작성하지 마.

## 명세서 양식
폴더: docs/<플랫폼>/features/<기능명>/ai/spec/
다른 문서(노트, 계획 step 파일, 목업 목차, 기록)가 이 파일 이름과 R·D 번호를 참조하므로, 정해진 파일 이름은 바꾸지 않는다.
아직 채울 내용이 없는 파일은 만들지 않고, index.md 표에 "(아직 없음)"이라고 적는다.

| 파일 | 내용 |
|---|---|
| index.md | 기능 개요(한두 줄), 요구사항 묶음 표(묶음 → 파일 → R 범위), 나머지 파일 표, 다른 문서(계획·테스트·기록) 링크 |
| req-<묶음>.md | 요구사항 묶음 하나 (화면이나 기능 단위). R 줄과 그 묶음의 표·보충 설명, 그 묶음 화면의 "화면 구성"(글이나 간단한 그림) |
| data.md | 다룰 데이터: 항목, 종류, 저장 위치 |
| scope.md | 이번 범위에서 제외하는 것, 나중에 고려할 것 |
| mockup.md | /mockup 명령이 채운다: 목업 경로(승인 날짜), "목업에서 정한 것", 목업에 넣은 추가 제안 |
| decisions.md | 결정 사항. 형식: `D번호. 내용 (적용: 계획 단계 범위 또는 "이후 전체") (기록: L번호)`. docs/common/ai/formats/record-format.md의 "결정 올리기"를 따른다 |

- 기능에 꼭 필요한 추가 내용(예: 확장 구조, 파일 구조, 창 설정, 완료 기준)은 extension.md, files.md, window.md, done.md처럼 따로 파일을 만들고 index.md 표에 올린다.
- 묶음 파일 이름은 영어 소문자·하이픈으로 짓는다 (예: req-gallery.md, req-status.md). 묶음이 아주 작으면(R 2~3개) 가까운 묶음과 한 파일에 둘 수 있다.
- 파일 하나가 150줄을 넘을 것 같으면 묶음을 더 잘게 나눈다.

req-<묶음>.md 형식:
```markdown
# <기능 이름> 요구사항: <묶음 이름> (R17–R22)

### <묶음 이름>
- R17. 한 문장에 요구사항 하나.
- R18. …
(표나 보충 설명은 R 줄 아래에 둔다)

## 화면 구성
(이 묶음 화면이 있을 때만)
```

## 기능 허브 양식
```markdown
# <기능 이름> (<기능명>)
한 줄 설명.

- 상태: 명세 완료 / 구현 중 (N/전체 단계 완료) / 완료
- 이어서 작업할 때: [notes.md](notes.md)만 먼저 읽는다. (노트가 생긴 뒤)

## 문서 색인 (필요한 색인만 열고, 거기서 필요한 파일만 읽기)
| 종류 | 색인 | 내용 |
|---|---|---|
| 명세서 | [ai/spec/index.md](ai/spec/index.md) | … |
| 구현 계획 | (아직 없음) | |
| 진행 기록 | [ai/logs/index.md](ai/logs/index.md) | |
| 목업 | (아직 없음) | |
| AI 테스트 | (아직 없음) | |
| 사용자 테스트 | (아직 없음) | |
```

## R 번호 규칙
- 요구사항마다 `R번호.`를 붙인다. 번호는 기능 안에서 R1부터 차례로 붙인다.
- 묶음은 화면이나 기능 단위로 나눈다. 번호는 묶음(파일)을 넘어 이어진다.
- 한 번 붙인 번호는 바꾸거나 다시 쓰지 않는다.
  - 요구사항을 새로 넣으면, 들어갈 묶음과 상관없이 지금까지 가장 큰 번호의 다음 번호를 쓴다. index.md 묶음 표의 R 범위도 고친다.
  - 요구사항을 없애면 줄을 지우지 않고 `- ~~R7. 내용~~ (삭제, L번호)`로 남긴다.
  - 내용을 바꾸면 같은 번호를 쓰고 줄 끝에 `(L번호에서 변경)`을 붙인다.
- 다른 문서에서 요구사항을 가리킬 때는 R 번호를 쓴다. 범위는 `R17–R22`처럼 적는다.
