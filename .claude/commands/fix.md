아래 문제를 고칠 거야.

$ARGUMENTS

기능 폴더는 docs/<플랫폼>/features/<기능명>/ 이다. 인자에 플랫폼이 없으면 `ls docs/*/features/`로 폴더 이름만 확인해 맞는 폴더를 쓴다. 두 플랫폼에 같은 이름이 있거나 어느 기능인지 분명하지 않으면 먼저 묻는다.
문제가 여러 개면 하나씩 이 순서를 따르고, 기록도 하나씩 남긴다.

## 0. /fix로 할 일인지 판단
| /fix로 한다 | 멈추고 수정 명세(`/spec`)를 권한다 |
|---|---|
| 명세대로 동작하지 않는 버그 | 새 요구사항(새 R 번호)·새 화면 |
| 문구·간격·색·작은 동작 조정 | 저장 데이터 구조·서버 테이블·서버 함수 변경 |
| 바뀌는 앱 코드 파일이 5개 미만 | 다른 기능이나 다른 앱에 걸치는 변경, 앱 사이 약속 변경 |

- 고치는 도중에 오른쪽으로 커지면 거기서 멈추고, 찾은 원인과 이유를 알려 수정 명세로 넘긴다. 이미 바꾼 코드는 되돌리고 알린다.
- PROJECT.md에서 그 기능 상태가 "완료"가 아니면(명세·계획·구현 중·테스트 대기·수정 중) /fix를 쓰지 않고 진행 중인 흐름에서 고치도록 알린다. 노트는 끝난 기능에서 낡아 있을 수 있으니 판단에 쓰지 않는다.

## 1. 찾기
- 기능 허브(index.md) → ai/spec/index.md에서 관련 묶음 파일만 찾아, 문제와 관련된 R 줄을 읽는다. 명세 전체·계획·옛 기록은 읽지 않는다.
- 결정(decisions.md)은 관련 D 번호가 보일 때만 그 줄을 읽는다.
- 코드는 grep으로 관련 파일만 찾아 읽고, 원인을 찾는다.

## 2. 재현
- 계산·로직 버그: 먼저 **실패하는 단위 테스트**를 쓴다 (PC: 원본 옆 `*.test.ts`·Vitest, 안드로이드: `app/src/test/`·JUnit). 예상 값은 명세의 R 줄과 사용자가 말한 기대 동작에서 가져오고, 지금 코드에서 가져오지 않는다. 테스트가 실패하는 것을 확인한다.
- 화면 문제: PC는 브라우저 미리보기(`desktop-web`, `?fixture=basic|empty`), 안드로이드는 가상 폰 + adb(docs/android/common/ai/testing.md)로 문제 상태를 직접 확인한다.
- 재현이 안 되면 고치지 않고, 확인한 내용과 함께 사용자에게 재현 방법을 묻는다.

## 3. 승인
- 명세대로 동작하지 않는 단순 버그(기대 동작이 R 줄이나 사용자 말로 분명함): 승인 없이 고친다.
- 동작·모양이 바뀌는 수정, 또는 기대 동작이 분명하지 않을 때: 원인, 고칠 방법, 바뀌는 파일, 명세 R 줄이 바뀌는지를 3~5줄로 보여주고 승인을 받은 뒤 고친다.

## 4. 고치기와 확인 (메인 세션이 직접, 하위 에이전트 없이)
- 그 플랫폼의 코드 규칙(apps/<플랫폼>/CLAUDE.md)을 따른다. 요청과 관계없는 정리·리팩터링은 하지 않는다.
- 확인 (실제로 실행한 것만 보고):
  - PC: `npm run build`, `npm test` (Rust를 고쳤으면 `cargo check`)
  - 안드로이드: `./gradlew assembleDebug`, `./gradlew test`
  - 2단계에서 쓴 테스트가 통과하는지, 화면 문제면 같은 방법으로 고쳐진 화면을 다시 확인한다 (고친 곳과 바로 옆 몇 군데만). 정식 /test 회차는 만들지 않는다.
- 사람이나 실제 환경만 확인할 수 있는 것(실제 서버·OS 기능 등)이 남으면 그 플랫폼의 출시 확인 목록(PC: docs/desktop/common/human/release-check.md)의 "대기"에 한 줄 올린다. 추가 칸은 `<기능명> fix L번호`. 안드로이드 목록이 아직 없으면 보고에만 적는다.

## 5. 기록
- 그 기능의 ai/logs/에 종류 "수정" 항목 하나를 남긴다 (docs/common/ai/formats/record-format.md). 제목은 `# LNN · 날짜 · 수정: <한 줄>`, "한 일"에 원인과 고친 방법을 적는다.
- 명세의 동작이 바뀌었으면 해당 R 줄을 고치고 끝에 `(LNN에서 변경)`을 붙인다 (spec.md의 R 번호 규칙). 앞으로 지킬 규칙이 생겼으면 decisions.md에 D 번호로 올린다.
- PROJECT.md 상태, 기능 허브 상태 줄, notes.md는 고치지 않는다.

## 6. 커밋과 보고
- 코드·테스트·기록을 한 커밋으로: `<기능 이름> 수정: <한 줄> (LNN)`. push는 하지 않는다.
- 보고: 원인, 고친 내용, 실행한 확인과 결과, 출시 확인으로 넘긴 것(있으면), 커밋. 그리고 push할지 묻는다.
