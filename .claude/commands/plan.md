"$ARGUMENTS" 기능의 구현 계획을 세워줘. 기능 폴더는 docs/features/<기능명>/ 이다.
- 명세서: ai/spec/index.md를 먼저 읽고, 계획에 필요한 req 파일·data.md·scope.md·decisions.md를 읽는다. 명세서를 찾지 못하면 계획을 세우지 말고 나에게 알려줘.
- 진행 기록: ai/logs/index.md(목차)를 확인하고 필요한 항목 파일만 읽는다.
- 목업: human/mockups/index.html 맨 앞 목업 목차를 보고 필요한 화면 파일만 읽는다. 목업은 화면 구성·흐름·문구의 근거이고, 색·크기·간격 같은 모양 값은 theme.css와 docs/common/ai/design/design-direction.md가 기준이다. 목차에 "폴리싱 이전 목업" 줄이 있으면 배치도 지금 앱 코드를 먼저 본다.
- 다른 기능의 구조가 필요하면 그 기능의 index.md에서 필요한 파일만 찾는다 (예: 메인 페이지 ai/spec/extension.md).

아직 코드는 작성하지 마.

계획에는 다음을 넣어줘.
1. 만들거나 수정할 파일 목록 (파일마다 어느 단계에서 만드는지)
2. 컴포넌트 구조
3. 구현 순서 (단계별)
4. 단계마다 내가 확인할 수 있는 결과
5. 단계마다 참고할 목업 화면 파일과 관련 요구사항 번호 (예: `part-status.html`, R18–R19)

## 수정 계획 (이미 구현한 기능의 요구사항이 바뀌었을 때)
ai/logs/index.md 목차에서 마지막 "계획" 항목보다 뒤에 "명세" 항목이 있으면 처음 계획이 아니라 **수정 계획**으로 세운다. 그 명세 항목(이하 "근거 기록", 예: L18)이 수정 범위를 정한다.
- 대상 R: 근거 기록에 적힌 바뀐 R과 새 R만 계획한다. req 파일은 통째로 읽되, 그 밖의 R은 다시 계획하지 않는다. 바뀐 R은 줄 끝의 `(L번호에서 변경)`으로 찾는다.
- 영향받는 R: 대상 R이 바꾸는 동작에 기대는 기존 R(예: 정렬 기준이 바뀌면 탭, 데이터가 바뀌면 달력·홈)을 찾아 따로 적는다. 이 R들도 고칠 코드가 있으면 단계에 넣는다.
- 결정: decisions.md에서 근거 기록 번호가 붙은 D(대체·변경)와 대상 R에 걸린 D를 찾아, 계획에서 무엇을 없애거나 바꾸는지 적는다.
- 기존 코드: 이전 계획의 structure.md(보관 폴더)로 관련 파일을 찾고, 그 파일들은 `grep -n "export"`로 함수 목록만 본다. 함수 이름으로 쓰는 곳을 grep해 함께 고칠 파일을 정한다. 코드를 통째로 읽지 않는다.
- 저장 데이터: 저장 모양이 바뀌면(속성·일정 종류를 없애거나 바꿈 등) 이미 저장된 파일을 새 모양으로 옮기는 단계를 넣는다. 언제 옮기는지와 원래 파일을 백업하는지는 계획에서 나에게 묻는다. 확인할 결과에는 옮기기 전후 예시 데이터를 적는다.
- 이전 테스트: 바로 전 회차 사용자 체크리스트에서 실패했거나 판정이 비어 있는 항목을 `grep -n "^### \|판정"`으로 찾는다. 그중 대상 R·영향받는 R과 관계있는 항목은 해당 단계의 확인할 결과에 넣는다.
- 목업: 바뀐 화면이 목업과 달라지면 어디가 달라지는지 step 파일에 적는다. 폴리싱으로 달라진 모양(색·간격·글씨 등)은 차이로 적지 않는다. 목업은 고치지 않는다. 화면 모양을 새로 정해야 하면 `/mockup`을 먼저 하자고 제안한다.

계획을 보여준 뒤 내가 승인하면 다음을 해줘.
- docs/features/<기능명>/ai/plan/에 나눠 저장:
  - index.md: 명세서·목업 링크, 작성일·상태, 계획 중 정한 결정과 작은 규칙, 단계 표(단계 → 이름 → step 파일 → R), 이번 계획에 넣지 않는 것 (40줄 안팎)
  - structure.md: 전체 파일 목록, 데이터 모양, 컴포넌트 구조, C++ 비유
  - step-NN.md: 단계 하나당 파일 하나. 요구사항(R), 목업 화면 파일, 할 일, 확인할 결과, 이 단계에서 만들거나 고칠 파일만 적는다
- ai/spec/index.md의 "다른 문서"에 계획 경로(승인 날짜)와 계획에서 정한 것 한두 줄을 기록
- 기능 허브(index.md)의 구현 계획 칸에 ai/plan/index.md 링크 추가
- 진행 기록에 "계획" 항목을 남기기 (docs/common/ai/formats/record-format.md의 "진행 기록 쓰는 법")
- 계획 중 정한 결정 중 앞으로 지켜야 할 것은 ai/spec/decisions.md에 D 번호로 올리기 (docs/common/ai/formats/record-format.md의 "결정 올리기")
- 같은 기능에 새 계획을 세울 때(이전 계획이 구현·테스트까지 끝난 뒤): 이전 plan/ 폴더를 archive/plan-<짧은 이름>/으로 옮기고 새 plan/을 만든다. 기능 허브의 보관 문서 표(없으면 만든다)에 옮긴 폴더를 올린다.

수정 계획이면 저장할 때 다음을 더 한다.
- plan/index.md 맨 위에 아래 네 줄을 둔다. `/implement`·`/test`·하위 에이전트는 이 줄로 수정 회차인지 알고 범위를 정한다.
  ```
  - 종류: 수정 계획 (근거 기록: L18)
  - 대상 R: R5, R8, R38–R40 …
  - 영향받는 R: R4, R7 … (없으면 "없음")
  - 커밋 접두어: <기능 이름> 수정1
  ```
- 단계 번호는 step-01부터 다시 붙인다. 커밋 이름은 "커밋 접두어 + N단계"라 이전 계획의 커밋과 겹치지 않는다.
- 작업 노트(notes.md)를 새로 쓴다: "완료"는 이전 계획을 한 줄로 줄이고(예: "이전 계획 10단계 + 사용자 테스트 r1 (archive/plan-initial/)"), "다음 진행"은 1단계, `- 수정 계획: 근거 기록 L18, 커밋 접두어 "<기능 이름> 수정1"` 줄, 관련 결정 순서로 쓰고, "확인할 문서"는 1단계에 필요한 파일로 채운다. 양식은 `.claude/agents/implement-step.md`의 "노트 쓰는 법"을 따른다.
- 기능 허브와 PROJECT.md의 상태 줄을 "수정 계획 승인 (구현 대기)"로 바꾼다.
