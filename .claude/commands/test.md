"$ARGUMENTS" 기능의 구현이 끝났어. 아래 순서대로 테스트를 진행해줘. 기능 폴더는 docs/<플랫폼>/features/<기능명>/ 이다 (아래 경로는 모두 이 폴더 기준).
- <플랫폼>은 desktop·android·web 중 하나다. 인자에 플랫폼이 없으면 `ls docs/*/features/`로 폴더 이름만 확인해 맞는 폴더를 쓴다 (대소문자·단수형 차이). 두 플랫폼에 같은 이름이 있으면 사용자에게 묻는다.
- 이 문서의 화면 확인·출시 확인은 PC 앱(desktop) 기준이다. 다른 플랫폼은 그 플랫폼의 테스트 방식이 정해질 때까지 화면 항목을 출시 확인으로 보낸다.

## 역할 나누기
- 메인 세션(이 문서): 테스트 계획, 하위 에이전트 띄우기, 출시 확인 후보 올리기, 색인·기록. **앱 코드를 읽지 않고 미리보기를 직접 열지 않는다.**
- AI 코드 테스트(빌드·코드 확인·순수 함수 실행)는 `test-ai`, AI 화면 확인(브라우저 미리보기)은 `test-ui` 하위 에이전트에 맡기고 판정 요약만 받는다. 수행 절차는 각 에이전트 정의(`.claude/agents/`)에 있으므로 메인은 읽지 않는다. 코드와 스크린샷이 메인 컨텍스트에 쌓이지 않게 하려는 것이다.
- 테스트 방식 설명: docs/desktop/common/ai/testing.md (메인은 필요할 때만 읽는다).

명령 실행 규칙 (메인도 같다): 경로는 절대 경로나 `(cd <경로> && …)`로 쓰고, 상대 경로 `cd`를 하지 않는다 (Bash의 현재 폴더는 호출 사이에 남는다). 없을 수 있는 폴더는 `2>/dev/null || true`를 붙인다.

## 0. 테스트 계획
아래 문서를 읽고 테스트 계획을 세워줘.
- 명세서: ai/spec/index.md, 모든 req-<묶음>.md, scope.md (테스트 항목은 요구사항마다 필요하므로 req 파일은 모두 읽는다)
- 구현 계획: ai/plan/index.md와 각 step 파일의 "확인할 결과"만 (`awk`나 grep으로 그 칸만 모아 읽는다)
- 진행 기록: 항목 파일을 통째로 읽지 않고, `grep -n "계획과 달라진 점\|테스트 메모\|남은 문제" ai/logs/L*.md`로 이 세 줄만 모아 읽기. 줄의 앞뒤 맥락이 더 필요할 때만 그 LNN.md를 읽는다
- 목업이 필요하면 human/mockups/index.html 목차를 보고 필요한 화면 파일과 그 화면의 CSS 클래스만 검색해서 읽기

문서를 찾지 못하면 테스트를 진행하지 말고 나에게 알려줘.

### 테스트 주체 나누기
| 주체 | ID | 맡는 것 |
|---|---|---|
| AI 코드 | A1… | 빌드·타입 검사·`cargo check`, 코드로 확인하는 규칙·계산 로직, 순수 함수 실행 (데이터 옮기기 함수 포함) |
| AI 화면 | V1… | 브라우저 미리보기에서 볼 수 있는 것: 표시·문구·흐름·누르기·입력·창 크기별 모습, 새로고침 뒤 데이터 유지. 예시 데이터(`?fixture=basic`·`empty`)로 시작 상태를 만든다 |
| 출시 확인 | C | 사람이나 실제 환경만 확인할 수 있는 것: 실제 서버·Google 로그인·Gmail·외부 사이트, Tauri·OS 기능(트레이·자동 시작·창 닫기·업데이트·설치·파일 저장 위치·앱 재시작 뒤 유지), 실사용 느낌 |

- 화면 항목은 먼저 AI 화면으로 보낸다. 미리보기에서 동작하지 않는 것(서버·Tauri 기능)만 출시 확인으로 보낸다.
- 예시 데이터에 없는 상태가 필요하면 화면에서 만들게 수행 방법에 적는다 (예: "새 지원으로 카드 하나 추가한 뒤"). 그래도 만들 수 없으면 출시 확인으로 보낸다.

### 수정 회차
ai/plan/index.md 맨 위가 "종류: 수정 계획"이면 수정 회차다. 이때는 위 문서 읽기와 아래 기준을 이렇게 바꾼다.
- 범위: plan/index.md의 "대상 R"과 "영향받는 R"만 테스트한다. 나머지 R은 이전 회차에서 통과했으므로 다시 하지 않는다.
- 명세서: req 파일은 대상 R·영향받는 R이 든 파일만 읽는다.
- 진행 기록: grep은 근거 기록(plan/index.md의 "근거 기록") 이후의 L 파일에만 한다.
- 이전 회차 다시 하기: 바로 전 회차 보고서(ai/tests/<전 회차>/index.md·ui.md의 결과 한눈에 보기)에서 실패·확인 불가 항목을 찾아 모두 이번 회차 항목에 넣는다. 테스트 이름 뒤에 "(r1 V3 다시)"처럼 이전 ID를 적는다.
- 영향받는 R: 바뀐 동작 때문에 깨질 수 있는 기존 동작을 회귀 항목으로 하나 이상 넣는다.
- 저장 데이터 옮기기(계획에 그 단계가 있을 때): AI 코드 테스트에 옮기기 함수를 계획의 전후 예시로 실행하는 항목을, 출시 확인에 "옛 형식 파일로 실제 앱을 켜 값이 제자리에 옮겨졌는지"를 넣는다.

계획을 세울 때 다음을 기준으로 해줘.
- 명세서의 요구사항마다 최소 하나 이상의 테스트 항목을 만든다 (수정 회차면 대상 R·영향받는 R마다).
- 구현 계획의 단계별 "확인할 결과"도 테스트 항목에 반영한다. 화면을 봐야 하는 결과는 빠짐없이 AI 화면이나 출시 확인 항목으로 넣는다.
- 정상 동작뿐 아니라 경계 상황과 예외 상황도 포함한다 (예: 빈 데이터, 잘못된 입력, 새로고침 뒤 데이터 유지).
- 명세서에서 "이번 범위에서 제외"한 기능은 테스트하지 않는다.
- 진행 기록의 "테스트 메모"는 빠짐없이 테스트 항목에 넣는다. "(자동 진행 중 판단)"으로 계획과 달라진 점이 있으면 그 부분도 항목에 넣는다.
- 화면 항목의 예상 결과는 눈에 보이는 글자·위치·상태로 적는다. 색·크기 같은 모양은 docs/desktop/common/ai/design/design-direction.md와 theme.css 토큰 이름으로 적는다.

계획을 표로 보여줘. 표에는 ID, 테스트 항목, 근거 요구사항, 예상 결과(한 줄), 주체(AI 코드 / AI 화면 / 출시 확인), AI 화면이면 시작 상태(예시 데이터 이름과 창 크기)를 넣어줘.
내가 승인하면 1~3번을 진행해줘. 회차는 r1, r2 …로 붙인다 (재테스트면 다음 회차).

## 1. AI 코드 테스트 (하위 에이전트 test-ai)
- `test-ai`를 하나 띄운다. 지시에는 기능명·플랫폼·회차, 승인된 AI 코드 항목 표, 임시 스크립트 폴더(이 세션의 scratchpad 경로)만 담는다.
- 에이전트가 없으면 general-purpose로 띄우고 지시 앞에 "`.claude/agents/test-ai.md`를 읽고 그대로 따라서"를 붙인다.
- 항목이 없으면 띄우지 않고 없다고 적는다.

## 2. AI 화면 확인 (하위 에이전트 test-ui)
- `test-ui`를 띄운다. 항목 15개마다 하나씩 나눠 띄운다 (한 에이전트의 대화가 길어지지 않게). 1번과 함께 띄워도 된다.
- 지시에는 기능명·플랫폼·회차, 승인된 AI 화면 항목 표(시작 상태 포함)만 담는다. 여러 개로 나누면 보고서 이름을 ui.md, ui-2.md …로 정해 준다.
- 에이전트가 없으면 general-purpose로 띄우고 지시 앞에 "`.claude/agents/test-ui.md`를 읽고 그대로 따라서"를 붙인다.
- 항목이 없으면 띄우지 않고 없다고 적는다.

하위 에이전트 결과를 받으면 `ls ai/tests/<회차>/`로 보고서 파일이 생겼는지만 확인한다. 보고서 내용은 다시 읽지 않는다. 실패 항목은 고치지 않는다. 보고할 때 실패 목록을 보여 주고 수정할지 나에게 물어봐줘.

## 3. 출시 확인 후보 올리기 (메인이 직접)
승인된 출시 확인 항목을 docs/desktop/common/human/release-check.md의 "대기" 표 맨 아래에 한 줄씩 추가한다. 형식과 규칙은 그 파일 맨 위에 있다. 기능마다 따로 체크리스트 파일을 만들지 않는다.

## 4. 문서 저장 후 (메인이 직접)
- ai/spec/index.md의 "다른 문서"와 기능 허브(index.md)의 테스트 칸에 이번 회차 보고서 경로(ai/tests/<회차>/index.md, ui.md)를 기록해줘.
- 이전 회차 테스트 문서는 move-doc 스크립트로 archive/tests/로 옮기고, 기능 허브의 보관 문서 표에 올려줘.
- 진행 기록에 "테스트" 항목을 남겨줘 (docs/common/ai/formats/record-format.md의 "진행 기록 쓰는 법"). 판정 수는 하위 에이전트의 요약을 그대로 쓰고, 출시 확인으로 올린 항목 수를 적는다.
- AI 코드·AI 화면 항목이 모두 통과하면 기능은 완료다. PROJECT.md 상태는 "완료"로 쓰고, 출시 확인으로 올린 항목이 있으면 "(출시 확인 N개)"만 덧붙인다.
- 한 번만 보고한다: AI 코드·화면 판정 요약(실패가 있으면 목록), 출시 확인으로 올린 항목 수.
