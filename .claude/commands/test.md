"$ARGUMENTS" 기능의 구현이 끝났어. 아래 순서대로 테스트를 진행해줘. 기능 폴더는 docs/<플랫폼>/features/<기능명>/ 이다 (아래 경로는 모두 이 폴더 기준).
- <플랫폼>은 desktop·android·web 중 하나다. 인자에 플랫폼이 없으면 `ls docs/*/features/`로 폴더 이름만 확인해 맞는 폴더를 쓴다 (대소문자·단수형 차이). 두 플랫폼에 같은 이름이 있으면 사용자에게 묻는다.

## 역할 나누기
- 메인 세션(이 문서): 테스트 계획, 하위 에이전트 띄우기, 사용자 테스트 체크리스트, 색인·기록. **앱 코드를 읽지 않는다.**
- AI 테스트 수행(빌드·코드 확인·순수 함수 실행·보고서 저장)은 하위 에이전트(Agent, `subagent_type: test-ai`)에 맡기고 판정 요약만 받는다. 수행 절차는 그 에이전트 정의(`.claude/agents/test-ai.md`)에 있으므로 메인은 읽지 않는다. 코드 내용이 메인 컨텍스트에 쌓이지 않게 하려는 것이다.

명령 실행 규칙 (메인도 같다): 경로는 절대 경로나 `(cd <경로> && …)`로 쓰고, 상대 경로 `cd`를 하지 않는다 (Bash의 현재 폴더는 호출 사이에 남는다). 없을 수 있는 폴더는 `2>/dev/null || true`를 붙인다.

## 0. 테스트 계획
아래 문서를 읽고 테스트 계획을 세워줘.
- 명세서: ai/spec/index.md, 모든 req-<묶음>.md, scope.md (테스트 항목은 요구사항마다 필요하므로 req 파일은 모두 읽는다)
- 구현 계획: ai/plan/index.md와 각 step 파일의 "확인할 결과"만 (`awk`나 grep으로 그 칸만 모아 읽는다)
- 진행 기록: 항목 파일을 통째로 읽지 않고, `grep -n "계획과 달라진 점\|테스트 메모\|남은 문제" ai/logs/L*.md`로 이 세 줄만 모아 읽기. 줄의 앞뒤 맥락이 더 필요할 때만 그 LNN.md를 읽는다
- 목업이 필요하면 human/mockups/index.html 목차를 보고 필요한 화면 파일과 그 화면의 CSS 클래스만 검색해서 읽기

문서를 찾지 못하면 테스트를 진행하지 말고 나에게 알려줘.

### 수정 회차
ai/plan/index.md 맨 위가 "종류: 수정 계획"이면 수정 회차다. 이때는 위 문서 읽기와 아래 기준을 이렇게 바꾼다.
- 범위: plan/index.md의 "대상 R"과 "영향받는 R"만 테스트한다. 나머지 R은 이전 회차에서 통과했으므로 다시 하지 않는다. 체크리스트 맨 앞에 "이번 회차 범위"(대상 R, 영향받는 R, 다시 하는 이전 항목)를 적는다.
- 명세서: req 파일은 대상 R·영향받는 R이 든 파일만 읽는다.
- 진행 기록: grep은 근거 기록(plan/index.md의 "근거 기록") 이후의 L 파일에만 한다.
- 이전 회차 다시 하기: 바로 전 회차 사용자 체크리스트에서 실패했거나 판정이 비어 있는 항목을 `grep -n "^### \|판정"`으로 찾아, 대상 R과 관계없어도 모두 이번 회차 항목에 넣는다. 테스트 이름 뒤에 "(r1 N번 다시)"처럼 이전 번호를 적는다.
- 영향받는 R: 바뀐 동작 때문에 깨질 수 있는 기존 동작을 회귀 항목으로 하나 이상 넣는다.
- 저장 데이터 옮기기(계획에 그 단계가 있을 때): AI 테스트에는 옮기기 함수를 계획의 전후 예시로 실행하는 항목을, 사용자 테스트에는 옛 형식 저장 파일로 앱을 켜서 값이 제자리에 옮겨졌는지 보는 항목을 넣는다. 체크리스트 "준비"에 옛 형식 파일을 구하는 방법(이전 회차 백업, 또는 AI가 human/tests/<회차>-data/에 만든 예시 파일을 앱 데이터 폴더에 복사)과 원래 파일을 백업하는 순서를 적는다.

계획을 세울 때 다음을 기준으로 해줘.
- 명세서의 요구사항마다 최소 하나 이상의 테스트 항목을 만든다 (수정 회차면 대상 R·영향받는 R마다).
- 구현 계획의 단계별 "확인할 결과"도 테스트 항목에 반영한다. AI는 화면을 띄워 확인하지 않으므로(`/implement`도 `/test`도), 화면을 봐야 하는 결과(표시·동작·창 크기별 모습)는 빠짐없이 사용자 테스트 항목으로 넣는다.
- 정상 동작뿐 아니라 경계 상황과 예외 상황도 포함한다.
  (예: 빈 데이터, 잘못된 입력, 앱 재시작 후 데이터 유지)
- 명세서에서 "이번 범위에서 제외"한 기능은 테스트하지 않는다.
- 각 항목을 AI 테스트와 사용자 테스트 중 어디에 넣을지 나눈다. AI 테스트는 화면 없이 할 수 있는 것(빌드·타입 검사·`cargo check`, 코드 읽기로 확인하는 규칙과 계산 로직 등)만 맡고, 앱을 띄워 보거나 눌러 봐야 하는 항목은 사용자 테스트로 보낸다.
- 진행 기록의 "테스트 메모"는 빠짐없이 테스트 항목에 넣는다. "(자동 진행 중 판단)"으로 계획과 달라진 점이 있으면 그 부분도 항목에 넣는다.

계획을 표로 보여줘. 표에는 ID(AI는 A1…, 사용자는 U1…), 테스트 항목, 근거 요구사항, 예상 결과(한 줄), 테스트 주체(AI / 사용자)를 넣어줘.
내가 승인하면 1번과 2번을 진행해줘. 회차는 r1, r2 …로 붙인다 (재테스트면 다음 회차).

## 1. AI 테스트 (하위 에이전트)
1. `test-ai` 하위 에이전트를 하나 띄운다. 넘길 지시에 다음만 담는다.
   - 기능명과 회차
   - 승인된 AI 테스트 항목 표 (ID, 항목, 근거 요구사항, 예상 결과)
   - 임시 스크립트를 둘 폴더: 이 세션의 scratchpad 경로
   - test-ai 에이전트가 없으면 general-purpose로 띄우고 지시 앞에 "`.claude/agents/test-ai.md`를 읽고 그대로 따라서"를 붙인다.
2. 1번을 띄운 뒤 결과를 기다리는 동안 2번 체크리스트를 쓴다 (서로 다른 파일만 다루므로 함께 진행해도 된다).
3. 결과를 받으면 `ls ai/tests/<회차>/`로 보고서 파일이 생겼는지만 확인한다. 보고서 내용은 다시 읽지 않는다.
4. 실패 항목은 고치지 않는다. 보고할 때 실패 목록을 보여 주고 수정할지 나에게 물어봐줘. 수행할 AI 테스트가 없으면 에이전트를 띄우지 않고 없다고 명시해줘.

## 2. 사용자 테스트 체크리스트 (초안)
승인된 계획 중 사용자 테스트 항목을 정리해서
human/tests/<회차>-user-test.md에 저장해줘. (사람이 위에서부터 차례로 보며 채우는 문서라 한 파일로 둔다)
결과 칸은 내가 직접 채울 거니까 비워 둬.

쓰기 전에 체크리스트에 넣을 화면 문구(버튼·메뉴·창 제목·안내 문구)를 확인한다. 앱 코드를 읽지 않고 `grep -rhoE` 로 한글 문구만 모아 본다 (예: `grep -rhoE '"[^"]*[가-힣][^"]*"' apps/desktop/src/pages/<기능 폴더> | sort -u`). 문구를 다 쓴 뒤에 고치지 않도록 먼저 모은다.

항목마다 다음 형식으로 적어줘.

### [번호]. 테스트 이름
- 근거 요구사항:
- 수행 방법: 무엇을 어떤 순서로 누르는지
- 예상 결과:
- 확인 위치: 화면 어디를 보면 되는지
- 실제 결과: (사용자 작성)
- 판정: [ ] 통과  [ ] 실패
- 메모: (사용자 작성)

화면 확인 항목은 AI가 직접 보지 않았으므로, 사람이 글만 보고 판단할 수 있게 적는다.
- 문서 맨 앞에 "준비" 칸을 두고, 여러 항목이 같이 쓰는 테스트 데이터를 만드는 순서를 한 번만 적는다 (예: 카드 3개 만들고 그중 하나에 27일 면접 일정 추가). 항목에서는 "준비의 카드 A"처럼 가리킨다.
- 창 크기가 걸린 항목은 크기(960x640, 1200x800, 최대화 등)를 수행 방법에 적는다.
- 예상 결과는 목업과 명세를 근거로 눈에 보이는 모습(색, 점선·흐림, 위치, 문구)을 구체적으로 적는다. "목업처럼 보임"처럼 적지 않는다.
  - 색·크기·간격·굵기 같은 모양은 목업 CSS 값이 아니라 docs/desktop/common/ai/design/design-direction.md와 앱의 theme.css 토큰으로 적는다. 목업 목차에 "폴리싱 이전 목업" 줄이 있으면 배치도 지금 앱 코드를 기준으로 적는다.
- 진행 기록의 "테스트 메모"와 "(자동 진행 중 판단)"으로 달라진 점은 해당 항목의 예상 결과에 반영한다.

확인할 것이 없으면 없다고 명시해줘.

## 3. 문서 저장 후 (메인이 직접)
- ai/spec/index.md의 "다른 문서"와 기능 허브(index.md)의 테스트 칸에 두 테스트 문서 경로를 기록해줘.
- 이전 회차 테스트 문서는 archive/tests/로 옮기고, 기능 허브의 보관 문서 표에 올려줘. 체크리스트에 딸린 이미지 등 같은 폴더의 파일도 함께 옮긴다.
- 구현 기록들의 "사용자 확인: 대기 (최종 테스트)"는 고치지 않는다. 사용자 테스트 결과 기록 항목 하나가 그 확인을 대신한다.
- 진행 기록에 "테스트" 항목을 남겨줘 (docs/common/ai/formats/record-format.md의 "진행 기록 쓰는 법"). 판정 수는 하위 에이전트의 요약을 그대로 쓴다. 사용자 테스트 결과가 나오면 같은 방식으로 한 항목 더 남겨줘.
- 한 번만 보고한다: AI 테스트 판정 요약(실패가 있으면 목록), 체크리스트 문서 경로.
