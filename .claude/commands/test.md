"$ARGUMENTS" 기능의 구현이 끝났어. 아래 순서대로 테스트를 진행해줘. 기능 폴더는 docs/features/<기능명>/ 이다.

## 0. 테스트 계획
테스트를 수행하기 전에 아래 문서를 읽고 테스트 계획을 세워줘.
- 명세서: ai/spec/index.md, 모든 req-<묶음>.md, scope.md (테스트 항목은 요구사항마다 필요하므로 req 파일은 모두 읽는다)
- 구현 계획: ai/plan/index.md와 각 step 파일의 "확인할 결과"
- 진행 기록: 항목 파일을 통째로 읽지 않고, `grep -n "계획과 달라진 점\|테스트 메모\|남은 문제" ai/logs/L*.md`로 이 세 줄만 모아 읽기. 줄의 앞뒤 맥락이 더 필요할 때만 그 LNN.md를 읽는다
- 목업이 필요하면 human/mockups/index.html 목차를 보고 필요한 화면 파일과 그 화면의 CSS 클래스만 검색해서 읽기

문서를 찾지 못하면 테스트를 진행하지 말고 나에게 알려줘.

계획을 세울 때 다음을 기준으로 해줘.
- 명세서의 요구사항마다 최소 하나 이상의 테스트 항목을 만든다.
- 구현 계획의 단계별 "확인할 결과"도 테스트 항목에 반영한다. AI는 화면을 띄워 확인하지 않으므로(`/implement`도 `/test`도), 화면을 봐야 하는 결과(표시·동작·창 크기별 모습)는 빠짐없이 사용자 테스트 항목으로 넣는다.
- 정상 동작뿐 아니라 경계 상황과 예외 상황도 포함한다.
  (예: 빈 데이터, 잘못된 입력, 앱 재시작 후 데이터 유지)
- 명세서에서 "이번 범위에서 제외"한 기능은 테스트하지 않는다.
- 각 항목을 AI 테스트와 사용자 테스트 중 어디에 넣을지 나눈다. AI 테스트는 화면 없이 할 수 있는 것(빌드·타입 검사·`cargo check`, 코드 읽기로 확인하는 규칙과 계산 로직 등)만 맡고, 앱을 띄워 보거나 눌러 봐야 하는 항목은 사용자 테스트로 보낸다.
- 진행 기록의 "테스트 메모"는 빠짐없이 테스트 항목에 넣는다. "(자동 진행 중 판단)"으로 계획과 달라진 점이 있으면 그 부분도 항목에 넣는다.

계획을 표로 보여줘. 표에는 테스트 항목, 근거가 되는 요구사항, 테스트 주체(AI / 사용자)를 넣어줘.
내가 승인하면 1번과 2번을 진행해줘.

## 1. AI 테스트 보고서
승인된 계획 중 AI 테스트 항목을 직접 수행하고, ai/tests/<회차>/ 폴더에 나눠 저장해줘.
회차는 r1, r2 …로 붙인다 (재테스트면 다음 회차).

앱이나 미리보기를 띄우지 않는다 (브라우저 도구·스크린샷을 쓰지 않는다). 화면 확인은 2번 사용자 테스트 체크리스트에 글로 적어 넘긴다.

- index.md: 테스트 환경, 결과 한눈에 보기(항목 ID → 판정 → 파일 표), 실패 항목, 참고 사항 (40줄 안팎)
- <묶음>.md: 항목별 결과를 명세서 req 묶음 단위로 나눠 적는다 (예: gallery.md, status.md). 묶음에 넣기 어려운 항목(빌드·코드 규칙 등)은 common.md

항목마다 다음을 적어줘.
- 테스트 내용
- 근거 요구사항
- 수행 방법 (실행한 명령어 등)
- 예상 결과
- 실제 결과
- 판정 (통과 / 실패)
- 실패한 경우 원인 추정과 수정 방향

실패한 항목은 바로 고치지 말고, 보고서를 보여준 뒤 수정할지 나에게 물어봐줘.
수행할 테스트가 없으면 없다고 명시해줘.

## 2. 사용자 테스트 체크리스트 (초안)
승인된 계획 중 사용자 테스트 항목을 정리해서
human/tests/<회차>-user-test.md에 저장해줘. (사람이 위에서부터 차례로 보며 채우는 문서라 한 파일로 둔다)
결과 칸은 내가 직접 채울 거니까 비워 둬.

항목마다 다음 형식으로 적어줘.

### [번호]. 테스트 이름
- 근거 요구사항:
- 수행 방법: 무엇을 어떤 순서로 누르는지
- 예상 결과:
- 확인 위치: 화면 어디를 보면 되는지
- 실제 결과: (사용자 작성)
- 판정: [ ] 통과  [ ] 실패
- 메모: (사용자 작성)

화면 확인 항목은 AI가 직접 보지 않았으므로, 사람이 글만 보고 판단할 수 있게 적는다.
- 문서 맨 앞에 "준비" 칸을 두고, 여러 항목이 같이 쓰는 테스트 데이터를 만드는 순서를 한 번만 적는다 (예: 카드 3개 만들고 그중 하나에 27일 면접 일정 추가). 항목에서는 "준비의 카드 A"처럼 가리킨다.
- 창 크기가 걸린 항목은 크기(960x640, 1200x800, 최대화 등)를 수행 방법에 적는다.
- 예상 결과는 목업과 명세를 근거로 눈에 보이는 모습(색, 점선·흐림, 위치, 문구)을 구체적으로 적는다. "목업처럼 보임"처럼 적지 않는다.
- 진행 기록의 "테스트 메모"와 "(자동 진행 중 판단)"으로 달라진 점은 해당 항목의 예상 결과에 반영한다.

확인할 것이 없으면 없다고 명시해줘.

## 3. 문서 저장 후
- ai/spec/index.md의 "다른 문서"와 기능 허브(index.md)의 테스트 칸에 두 테스트 문서 경로를 기록해줘.
- 이전 회차 테스트 문서는 archive/tests/로 옮기고, 기능 허브의 보관 문서 표에 올려줘.
- 구현 기록들의 "사용자 확인: 대기 (최종 테스트)"는 고치지 않는다. 사용자 테스트 결과 기록 항목 하나가 그 확인을 대신한다.
- 진행 기록에 "테스트" 항목을 남겨줘 (/implement 명령의 "진행 기록 쓰는 법"). 사용자 테스트 결과가 나오면 같은 방식으로 한 항목 더 남겨줘.
- 내가 사용자 테스트를 진행할 수 있게 체크리스트 문서 경로를 알려줘.
