# 서버 연결: 결정 사항

- D1. 서버 연결은 선택이다. 연결하지 않아도 로컬 기능은 모두 동작하고, 서버가 필요한 화면만 "서버 연결 필요"를 보여준다. (적용: 이후 전체) (기록: L01)
- D2. 서버 구조는 번호 단계로 관리하고, 앱이 서버 번호를 비교해 뒤처지면 PAT를 받아 빠진 단계를 적용한다. 각 기능은 새 단계를 추가하고 배포한 단계는 고치지 않는다. (적용: 이후 전체) (기록: L01)
- D3. 로그인은 Supabase Auth의 Google 로그인만 쓰고, 자동 세팅 때 처음 로그인한 Google 계정 하나만 허용한다. (적용: 이후 전체) (기록: L01) (L02에서 변경)
- D4. 주소·anon 키는 앱 설정 파일, 로그인 토큰은 Windows 자격 증명 관리자에 두고, PAT와 Anthropic 키는 저장하지 않는다. (적용: 이후 전체) (기록: L01)
- D5. Daybrick 서버 테이블은 모두 `user_id`와 본인 행만 허용하는 RLS를 가진다. (적용: 이후 전체) (기록: L01)
- D6. 설정 화면은 사이드바 맨 아래 Settings 메뉴로 두고, 기능마다 칸을 추가한다. (적용: 이후 전체) (기록: L01)
- D7. 설치 가이드는 앱 안 연결 단계 화면에 두고, 입력칸마다 "어디서 찾나요?" 도움말을 둔다. (적용: 이후 전체) (기록: L01)
- D8. 일시정지는 대시보드 링크와 PAT로 바로 재개하는 방법을 함께 안내한다. (적용: 이후 전체) (기록: L01)
- D9. 로그인 때는 이메일 확인 권한만 받고, Gmail 읽기 권한은 Gmail을 쓰는 기능이 연결할 때 같은 Google 계정에 추가로 받는다. (적용: 이후 전체) (기록: L02)
- D10. Google OAuth 클라이언트는 사용자가 자기 Google Cloud에서 만들며, 서버 연결 처음 세팅의 필수 단계다. (적용: 이후 전체) (기록: L02)
- D11. Supabase 관리 API, Anthropic 키 사전 확인, Google 로그인 결과 수신은 Rust에서 한다. PAT·키는 호출마다 인자로만 넘기고 Rust도 저장하지 않는다. (적용: 4~9단계) (기록: L05)
- D12. 계정 하나만 허용하는 방법: 자동 세팅의 첫 로그인 직후 PAT로 인증 설정의 새 가입 막기(`disable_signup`)를 켠다. 자동 세팅 다시 실행도 켠 상태를 유지한다. (적용: 이후 전체) (기록: L05)
- D13. Google 로그인 결과는 PKCE와 `http://127.0.0.1:<임시 포트>/auth/callback`에서 한 번만 받는 Rust 수신기로 넘겨받는다. (적용: 이후 전체) (기록: L05)
- D14. Windows 자격 증명 관리자에는 refresh 토큰만 저장하고, 앱을 켤 때 그 토큰으로 세션을 다시 받는다. (적용: 이후 전체) (기록: L05)
- D15. 서버 구조 단계 SQL은 `supabase/migrations/NNNN_*.sql`, 서버 함수는 `supabase/functions/`에 두고 Rust가 빌드 때 포함한다. 앱의 최신 번호 기준은 Rust `migrations.rs`. (적용: 이후 전체) (기록: L05)
- D16. 서버 함수는 단계별로 나누지 않고 앱이 가진 최신 묶음을 매번 다시 배포한다. SQL 단계는 번호 기록과 함께 한 트랜잭션으로 적용한다. (적용: 이후 전체) (기록: L05)
- D17. 접속 확인은 로그인 전에는 공개 RPC `daybrick_schema_version()`, 로그인 뒤에는 `health` 서버 함수로 하고, 둘 다 DB를 실제로 읽는다. (적용: 이후 전체) (기록: L05)
- D18. 서버 연결 화면에서 쓰는 아이콘(서버·새로고침·열쇠 등)은 `components/icons/ServerIcons.tsx`에 모은다. (적용: 이후 전체) (기록: L06)
- D19. `clear_server_connection`은 server.json을 통째로 지우고, `ServerProvider.clearConnection`이 그 뒤 `welcomeDismissed: true`만 든 설정을 다시 저장한다. 연결 해제 뒤에는 첫 실행 안내 대신 설정의 "연결 안 함" 칸이 보인다. (적용: 6, 9단계) (기록: L06)
- D20. 연결 마법사가 열려 있는지는 `ServerProvider`의 `setupOpen`·`openSetup()`·`closeSetup()`로 공유하고, 입력값·지금 단계는 마법사 안의 `useWizard`에만 둔다 (마법사가 닫히면 함께 사라짐). 어느 화면을 그릴지는 `App.tsx`의 `AppScreens`가 정하고, 사이드바 없는 화면은 `TitleBar`를 `onToggleSidebar` 없이 그려 앱 이름만 보인다. (적용: 이후 전체) (기록: L07)
- D21. 첫 실행 안내·마법사의 버튼은 `wizard/WizardShell.css`의 `setup-btn`(`--primary`·`--ghost`·`--lg`)을 쓴다. 마법사 단계 화면은 `wiz-form__inner` 안에 그린다. (적용: 3~8단계) (기록: L07)
- D22. 마법사 입력칸·"어디서 찾나요?"·결과 줄은 `wizard/WizardFields.css`의 `wiz-field`·`wiz-input`(`--ok`·`--bad`)·`wiz-help`·`wiz-help-pop`·`wiz-alert`(`--ok`·`--bad`·`--warn`·`--info`)를 쓰고, 도움말 내용은 `guides.ts`의 `FIELD_HELPS`, 비밀값 칸은 `SecretInput`, 외부 링크는 `wizard/openExternal.ts`로 연다. (적용: 4~9단계) (기록: L08)
- D23. 마법사 갈래는 `useWizard`의 `route`(`KeysRoute`: setup·login·login-update·app-update, ② 확인 성공 때 정해짐)로 `ROUTE_STEPS`에서 네 칸을 고른다. 셋째 칸 이름은 "자동 세팅"/"로그인"/"앱 업데이트". 아직 화면이 없는 칸은 `WizardShell`의 `PendingStep`이 그리고, 6·8단계가 그 자리를 화면으로 바꾼다. 서버 업데이트는 login-update 갈래의 로그인 뒤에 끼워 넣는다. (적용: 4~8단계) (기록: L08)
- D24. 앱의 최신 서버 구조 번호는 Rust `migrations.rs`의 마지막 번호다. 프론트는 `features/server/management.ts`의 `getAppSchemaVersion()`(명령 `latest_schema_version`, 한 번 받아 기억)으로 받고, ② 확인 결과 `KeysCheck`(kind "ok")의 `appSchema`에 담는다. `routeForSchema(schema, appSchema)`. (적용: 5, 8단계) (기록: L08) (L10에서 변경)
- D25. Rust의 바깥 API 호출(관리 API·Anthropic)은 `server/http.rs`의 `client()`·`network_error`·`check_status`를 쓰고, 실패는 원인 종류 코드(`unauthorized`·`forbidden`·`not-found`·`rate-limited`·`server`·`network`·`bad-response`)만 돌려준다. 프론트는 `features/server/management.ts`의 `ApiResult`·`ApiErrorKind`로 받고, SQL은 `management.rs`의 `run_query`(`POST …/database/query`, 결과 행 배열)로 실행한다. (적용: 5~9단계) (기록: L09)
- D26. ③ 자동 세팅 단계 안의 화면은 `useWizard`의 `setupPhase`("input"/"run")로 나눈다. [세팅 시작] 사전 확인을 통과하거나 "빈 프로젝트가 아닙니다" 팝업에서 [그래도 계속]을 누르면 "run"이 되고, 실행 화면은 `WizardShell.renderStep()`의 `setup` 칸 run 자리(지금은 `PendingStep`)에 그린다. run에서 [이전]은 입력 화면으로 돌아간다. (적용: 5~6단계) (기록: L09)
- D27. ③ 실행 단계 정의(`RUN_STEPS`, 진행 중 글을 바꿀 땐 `running`)·타입(`RunStepId`·`RunStepState`·`RunProgress`·`RunErrorKind`)과 단계별 동작 표 `ACTIONS`(여섯 단계 모두)는 `features/server/setupRunner.ts`에 둔다. 동작은 `RunContext`(비밀값, `appSchema`, `login()`, `onVerified`)를 받고, `login()`은 이미 로그인했으면 그 세션을 돌려준다. 실행 상태는 `useWizard`의 `runProgress`·`running`·`runOutcome`("done"/"failed"/"stopped")·`retryRun`, 실행 중에는 `canCancel`·`canGoPrev`가 꺼지고, "done"이면 스스로 ④로 간다. 실패 문구는 `messages.ts`의 `runFailMessage`. (적용: 6, 8단계) (기록: L10) (L11에서 변경)
- D28. `apply_migrations(pat, projectRef)`는 시작 번호를 인자로 받지 않고 매번 서버의 지금 번호(구조 기록 테이블이 없으면 0)를 읽어 그 다음부터 적용하고 `{ from, to }`를 돌려준다. 서버 업데이트(8단계)도 같은 명령을 쓴다. (적용: 8단계) (기록: L10)
- D29. 로그인한 세션으로 부르는 서버 쪽 작업(`health`·`ai-key-check` 서버 함수, `daybrick_server_state` 본인 행 기록)은 `features/server/serverFunctions.ts`의 `fetchHealth`·`checkServerAiKey`·`recordKeyRegistered`를 쓰고 실패는 `ApiErrorKind`로 받는다. Anthropic 키 등록일은 자동 세팅 "계정 등록" 단계 시각으로 기록한다(키 교체 때도 같은 함수). (적용: 7, 9단계) (기록: L11)
- D30. 로그인 세션은 `ServerProvider`의 `session`(`ServerSession`: client·userId·email)·`sessionReady`·`completeLogin(connection, session)`으로 공유한다. `completeLogin`이 연결 정보를 server.json에 처음 저장한다. 세션 클라이언트는 `session.ts`의 `createSessionClient`(PKCE, 자동 갱신, 토큰이 바뀌면 자격 증명 관리자 `Daybrick/<ref>`에 저장)로 만들고, 켤 때 `restoreSession`, 로그아웃은 `signOut`, 연결 해제는 `clearConnection`이 `deleteSavedLogin`으로 지운다. Google 로그인은 `googleLogin.ts`의 `signInWithGoogle`(Rust `start_oauth_listener`·`wait_oauth_callback`·`cancel_oauth_listener`)이고 실패는 `LoginErrorKind`. (적용: 이후 전체) (기록: L11)
- D31. 마법사 아래 버튼 줄은 `WizardFooter`의 `next`(`FooterNext` 또는 null이면 오른쪽 버튼 없음)·`hideBack`(취소·이전 숨김)으로 그린다. 가이드가 없는 단계는 `wiz-main--full`로 가이드 칸 없이 그리고, 가운데 정렬 화면은 `wizard/CenterCard.css`의 `wiz-center`(`--boxed`)·`wiz-big-mark`(`--ok`·`--info`·`--bad`)·`wiz-summary`·`wiz-next-list`를 쓴다. [Google로 로그인]은 `wizard/GoogleButton.tsx`(설정 화면도 이것). 마법사 로그인 상태는 `useWizardLogin`(`phase`·`loginUrl`·`startLogin`·`cancelLogin`). (적용: 8~9단계) (기록: L11)
- D32. 서버 상태·접속 확인은 `ServerProvider`의 `status`(연결 정보 있고 첫 확인 전이면 "connected")·`checking`·`recheck()`·`resuming`·`resumeChecks`·`startResume()`로 공유한다(내부는 `useHealthCheck`, 판정은 `health.ts`의 `checkServerStatus`, 결과는 server.json `lastCheck`). 띠 문구·색은 `messages.ts`의 `BANNER_TEXTS`, [×] 숨김은 `dismissedBanners`·`dismissBanner(status)`(상태 종류별, 메모리만). 띠는 `AppLayout`의 `banner` 자리에 `ServerBanner`로 넣고, `OverlayRootContext`는 띠까지 감싼다. 서버가 필요한 화면은 `components/server/ServerRequired`를 넣는다. (적용: 이후 전체) (기록: L12)
- D33. 상태 판정: 로그인 안 했으면 공개 RPC로 보고 서버 번호 > 앱이면 "app-update", 접속되면 그 밖은 "login-needed"(서버 업데이트 필요는 로그인 뒤에 판정). 로그인했으면 `health`로 번호 비교, 실패하면 공개 RPC로 일시정지·접속 불가를 가르고 401은 "login-needed", 404(함수 없음)는 "server-update". 저장된 키가 거절돼도 "unreachable". 세션이 없으면 확인마다 `ensureSession`으로 저장된 로그인을 다시 받아 본다. (적용: 8~9단계) (기록: L12)
- D34. 재개는 `management.ts`의 `requestResume(pat, ref)`(Rust `project_status`를 먼저 보고 `INACTIVE`일 때만 `restore_project`)를 쓰고, 성공하거나 [대시보드에서 재개]를 누르면 `startResume()`으로 10초마다 확인한다. 일시정지 상태 글자 `INACTIVE`와 `POST …/restore` 경로는 추측이다. (적용: 9단계) (기록: L12)
- D35. 단계 목록 실행 고리는 `setupRunner.ts`의 `runSteps(count, actionAt, …)`(자동 세팅 `runSetup`과 서버 업데이트가 함께 씀)이고, 서버 업데이트 단계(`UPDATE_STEPS`: schema·functions·verify, 자동 세팅과 같은 id)·실행 상태(`useServerUpdateRun`)·서버/앱 번호 읽기(`useSchemaPair`, 공개 RPC)는 `features/server/serverUpdate.ts`에 둔다. 단계 목록 화면 `RunStepList`와 `runFailMessage`는 `flow`("setup"/"update")로 목록을 고른다. (적용: 9단계) (기록: L13)
- D36. 서버 업데이트 화면은 `ServerProvider`의 `updateOpen`·`openUpdate()`·`closeUpdate()`로 본문 자리에 열고(사이드바 그대로), 메뉴 이동·뒤로·앞으로를 하면 닫힌다(`App.tsx`의 `AppMain`이 navigate를 감쌈, `ServerProvider`는 `NavigationContext` 바깥). 화면 몸체는 `ServerUpdateScreen.tsx`의 `ServerUpdatePanel`(마법사 login-update 갈래의 로그인 뒤에도 씀, `embedded`)이고, 앱 업데이트 안내는 `AppUpdateNotice`(설정 칸·마법사 app-update 칸). 서버 기능은 세션을 `serverSession`으로 받는다: "server-update"·"app-update" 상태면 null (R24, R25). 서버 연결 화면만 `session`을 쓴다. (적용: 이후 전체) (기록: L13)
- D37. Rust `configure_auth`·`set_secrets`는 빈 값을 보내지 않아 서버의 지금 값을 그대로 둔다(`set_secrets`는 모두 비면 부르지 않음). Anthropic 키 교체는 키만, 자동 세팅 다시 실행은 Google ID·비밀값을 둘 다 넣었을 때만 바꾼다. (적용: 이후 전체) (기록: L14)
- D38. 설정 서버 연결 칸은 `ServerSection`이 연결 없음 → `ServerSectionOff`, "app-update" → 안내, `session` 있음 → `ServerSectionConnected`, 없음 → `ServerSectionLogin`으로 나누고, 머리 상태 글자·색은 `messages.ts`의 `SETTINGS_STATE`. 로그아웃은 `ServerProvider.logout()`, 해제·바꾸기는 `ServerDangerRow`(`ConfirmDialog`의 `note`·`confirmTone`), 작은 창 틀은 `SettingsDialog`, 다시 실행은 `features/server/rerunSetup.ts`(`RERUN_STEPS`·`useRerunSetup`, `RunStepList`의 `flow="rerun"`)와 `setupRunner.ts`의 `verifyServer(session, appSchema)`. (적용: 이후 전체) (기록: L14)
