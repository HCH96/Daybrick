# L17 · 2026-10-27 · 구현 13단계: Gmail 연결·해제

- 요구사항: R60–R63, R70
- 시작 전 확인: server-setup 마법사(guides.ts)는 Google 클라이언트를 "웹 애플리케이션" 유형으로 만들고 Supabase 콜백 주소만 등록한다 (코드로 확인). 웹 클라이언트는 등록된 주소·포트가 정확히 같아야 해 임의 포트 127.0.0.1 리디렉션을 못 받는다고 판단했다 (Google 문서 지식, 실행 확인 안 함). 그래서 멈추고 사용자와 맞췄다.
- 사용자 결정: B 방식. 앱 로그인과 같은 Supabase Google 로그인을 잠깐 쓰는 클라이언트로 열어 `provider_refresh_token`을 받아 메모리로만 `js-gmail`에 넘긴다. 다른 Google 계정을 고르는 경우는 다루지 않는다 ("구글 로그인은 원래 메일 때문에 시키는 것").
- 한 일: `js-gmail`(connect: Google 토큰 갱신으로 살아 있는지·gmail.readonly 허락 여부 확인 → AES-GCM 암호화 저장, 권한이 빠졌으면 토큰 취소 후 no-scope / disconnect: 복호화 → Google revoke → 행 삭제, revoke 실패해도 행은 지우고 `revoked:false`). `js-gmail/token.ts`에 암호화·토큰 호출·`storedAccessToken`(거절이면 `broken_at`, 14단계용). `migrations.rs` 함수 묶음에 js-gmail 추가.
- 앱: `gmailConnect.ts`(잠깐 쓰는 PKCE 클라이언트, `login_hint`=로그인 이메일, 끝나면 그 세션 로그아웃), `gmailApi.ts`, `GmailPanel`(연결 전: [Gmail 연결]+"앱에 로그인한 계정의 Gmail이 연결돼요"+확인되지 않은 앱 안내 / 기다리는 중: 브라우저 다시 열기·취소 / 연결됨: 계정 상자·마지막 확인·[연결 해제] / 끊김: 빨간 "다시 연결 필요"·[다시 연결]).
- 결정: D18 변경(사용자 결정), D41 추가
- 계획과 달라진 점: 인증 방식 B (사용자 승인). 앱 쪽 서버 호출은 `api.ts` 대신 새 파일 `gmailApi.ts`, 서버 공용 코드는 `js-gmail/token.ts`로 나눴다. 이메일 일치 검사는 하지 않고 저장 이메일은 서버의 로그인 계정 이메일을 쓴다. (자동 진행 중 판단)
- 확인: `npm run build` 성공, `cargo check` 성공. 서버 함수(Deno)는 이 PC에 deno가 없어 타입 검사를 못 했다. 화면·서버 동작은 실행해 보지 않았다.
- 사용자 확인: 대기 (최종 테스트)
- 테스트 메모: 실행 확인 못 한 것 — ① `access_type=offline`+`prompt=consent`로 Supabase가 `provider_refresh_token`을 실제로 주는지(안 오면 "연결 토큰을 주지 않았어요") ② [연결 해제]의 Google 권한 취소가 앱 로그인(Supabase 세션)·다음 앱 Google 로그인에 영향이 있는지. 동의 화면에서 Gmail 체크를 풀면 "Gmail 읽기 권한이 허락되지 않았어요"가 떠야 한다. 서버 업데이트(함수 배포) 후에 확인한다.
