# 구직 관리 (job-search) 사용자 테스트 체크리스트 r2
- 작성일: 2026-10-29 · 범위: 수정1(중복 공고 묶기)의 주요 기능 동작만 (사용자 요청으로 간단하게. 세부 규칙은 AI 테스트에서 확인)
- 근거: 테스트 계획 r2 (U1–U14), AI 테스트 보고서 [r2/](r2/)
- 화면은 AI가 직접 보지 않았다. 예상 결과는 명세·진행 기록 기준이다.

## 이번 회차 범위
- 대상 R: R35, R41, R82–R93
- 영향받는 R: R4, R7, R9, R15–R16, R24, R28, R33, R39–R40, R46–R47, R53, R55, R80
- 다시 하는 이전 항목: r1 7번(실패), r1 8–16번(판정 비어 있음)

## 준비
1. 테스트용 Supabase·Anthropic 키로 연결된 앱을 `npm run tauri dev`로 켠다.
2. 업데이트 전 공고가 서버에 남아 있는지 본다 (r1에서 수집한 게임잡 공고). 소급 묶기(U3)는 이 공고로 확인한다.
3. 프로필이 저장되어 있어야 한다 (r1 3번). Gmail 확인용 다른 계정이 없으면 U11·U12는 건너뛴다.
4. **묶음 데이터 만들기:** 실제 사이트끼리 같은 공고가 없을 수 있으므로, 게임잡 어댑터로 사이트를 하나 더 만든다. 수집 사이트 탭 [사이트 추가] → 이름 "게임잡 자사", 주소·어댑터·사이트별 값은 기존 게임잡과 같게 → 자사 체크를 켬 → [시험 수집] → [저장]. (같은 주소로 사이트를 하나 더 만들 수 있음을 AI 테스트 A11에서 확인했다. 이름을 "게임잡 자사"로 다르게 해야 출처 줄에서 구별된다.)
- 이후 "묶음 카드"는 U3 뒤 카드 아래줄에 "출처: …"가 있는 카드를 뜻한다.

### 1. 서버 업데이트와 자사 칸

### 3. 수집·평가 뒤 같은 공고 묶기
- 근거 요구사항: R35, R82–R87, R89
- 수행 방법: 수집 사이트 탭 [지금 수집] → 끝나면 추천 공고 탭 처리 줄의 [지금 평가] (처리가 끝날 때까지 기다린다) → Supabase SQL 편집기에서 `select dedupe_version from js_settings` 와 `select s.name, p.title, p.stage, p.dup_of is not null as bundled, p.body_text is null as no_body from js_postings p join js_sites s on s.id = p.site_id order by p.title limit 20` 를 실행한다.
- 예상 결과: `dedupe_version`이 1이다. 같은 제목의 공고가 "게임잡"과 "게임잡 자사"에 하나씩 있고, 게임잡 쪽이 `stage duplicate`·`bundled true`(묶인 쪽), 게임잡 자사 쪽이 대표(`bundled false`)다. 게임잡 쪽은 이미 채점됐어도 대표의 점수가 그대로 이어지고 다시 채점하지 않는다. 추천 공고 탭에 같은 공고가 두 장으로 보이지 않는다.

### 6. 따로 보기
- 근거 요구사항: R93
- 수행 방법: 묶음 카드 팝업에서 "게임잡" 줄의 [따로 보기] → [지금 평가] → 추천 목록을 본다 → [지금 수집]·[지금 평가]를 한 번 더 한다. 다른 묶음 카드에서는 "(대표)" 줄의 [따로 보기]를 누른다.
- 예상 결과: 묶인 공고를 풀면 "따로 볼게요. 다음 처리 뒤 별도 공고로 보여요."가 뜨고 그 출처 줄이 사라진다. 평가 뒤 풀린 공고가 별도 카드로 나오고, 다시 수집·평가해도 다시 묶이지 않는다. 대표를 풀면 팝업이 닫히고, 남은 공고가 새 대표로 같은 점수로 보이며, 풀린 옛 대표는 평가 뒤 별도 카드가 된다.
- 확인 위치: 상세 팝업 출처 블록, 추천 공고 탭 카드 목록
- 실제 결과: (사용자 작성)
- 판정: [ ] 통과  [ ] 실패 [O] 보류
- 메모: [따로 보기] 누르면 묶음이 나뉘는 것까지 확인. 원문 대기 약 300개로 [지금 평가]가 너무 오래 걸려, 평가 뒤 별도 카드 표시·재수집 뒤 다시 묶이지 않는지·대표 풀기는 이번에 확인 못 함.
