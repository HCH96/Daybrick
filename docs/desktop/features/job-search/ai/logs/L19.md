# L19 · 2026-10-27 · 구현 15단계: 예약 실행과 알림

- 요구사항: R33, R36, R74, R78, R80–R81
- 한 일: 서버 구조 4번 `0004_job_search_cron.sql`: pg_cron·pg_net 켜기, vault의 예약 비밀값·프로젝트 주소로 서버 함수를 부르는 `js_cron_call`, 작업 3개(주간 수집 일 21:00 UTC, 이어 하기 15분마다, 메일 확인 매일 22:00 UTC)와 각 조건 함수.
- `_shared/auth.ts`: `x-daybrick-cron` 머리글이 `DAYBRICK_CRON_SECRET`과 같으면 가장 먼저 만든 사용자로 처리(`Caller.viaCron`), 머리글이 틀리면 거절.
- 알림 6종 연결: 수집 실패(`js-collect`, 시간 부족 건너뜀은 제외), 새 추천 공고(`js-process` queue가 대기열을 비웠을 때), 메일 제안(`js-gmail check`, 처리 안 한 제안 전체 수), 한도 80%·초과·크레딧 부족(`_shared/ai.ts`, 기간마다 한 번), Gmail 끊김(`markBroken`이 처음 끊길 때만).
- 앱: 알림의 `tab` 열기는 `JobSearchPage`의 `usePageIntent`가 이미 처리해 고치지 않았다.
- 결정: D43 추가
- 계획과 달라진 점: (자동 진행 중 판단)
  - "예약 비밀값을 vault에 넣는 RPC"는 만들지 않았다. 2단계의 Rust가 vault에 넣고, 서버 함수 주소용 `daybrick_project_url`도 같은 "비밀값 만들기" 단계(`management.rs`)에서 넣는다.
  - pg_net 호출에 JWT를 싣지 않으려고 js-collect·js-process·js-gmail은 게이트웨이 JWT 확인을 끄고 배포한다(`EdgeFunction.verify_jwt`). 호출자 확인은 함수 안 `getCaller`가 그대로 한다.
  - "수집 끝나면 js-process"는 pg_net이 응답을 기다리지 않아, 15분 이어 하기 작업이 새 공고를 보고 부르는 방식으로 했다. 원문을 못 받은 공고를 위해 `js-collect { action: "bodies" }`를 더했다.
  - 고친 파일 더함: `management.rs`, `js-gmail/token.ts`. `JobSearchTabs.tsx`는 고치지 않음.
- 확인: `npm run build` 성공, `cargo check` 성공. 서버 함수는 임시 폴더의 Deno 대용 타입 선언 + `tsc`로 js-collect·js-process·js-gmail·js-profile 타입 검사만 통과. SQL·예약 실행·알림은 실제 서버에서 실행해 보지 않았다.
- 무료 플랜 확인: pg_cron·pg_net·vault는 Supabase 문서상 무료 플랜에서 쓸 수 있다(실제 서버로 확인하지 않음, 추측).
- 사용자 확인: 대기 (최종 테스트)
- 테스트 메모: 서버 업데이트(4번 적용·함수 배포·비밀값 만들기)를 한 번 해야 예약이 돈다. 주간 수집 시각 바꾸기는 `select cron.schedule('js-weekly-collect', '<분> <시> * * *', 'select public.js_cron_weekly_collect()')`(UTC). "새 추천 공고" 알림은 처리 대기열이 0이 된 실행에서만 오므로 수집 뒤 최대 15분×(공고 수/5) 걸린다. 한도 알림은 같은 날(월 한도는 같은 달)에 한 번만 온다.
