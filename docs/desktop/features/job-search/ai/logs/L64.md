# L64 · 2026-11-11 · 수정: 이미지 큰 공고에서 일괄 맡기기가 메모리 한도로 죽는 문제

- 요구사항: R38, R102, R106
- 한 일: [지금 평가]와 예약 처리가 11/10 19:22(한국 시간)부터 매번 "일괄 처리를 맡기지 못했어요. 서버에서 오류가 났어요."로 실패함.
  함수 로그로 보니 `js-process` batch가 매번 546(Memory limit exceeded)으로 꺼졌고, 같은 순서로 같은 공고를 다시 집어 대기열이 막혀 있었음.
  원인: 긴 투명 PNG를 PDF로 바꿀 때 압축을 통째로 풀고 행 필터 되돌리기·흰 바탕 합치기에서 사본을 더 만들어, 2,000만 픽셀 하나에 메모리를 약 263MB 씀.
  고친 방법: 투명 PNG를 줄 단위로 풀어 합치고 바로 다시 압축하도록 바꿈 (결과 바이트는 같음). 맡길 때 요청 글자를 이어 붙인 사본까지 메모리에 같이 있으므로 일괄 하나의 크기 상한을 30MB → 10MB로 줄임.
- 결정: D71 변경 (일괄 나누기 크기 약 30MB → 약 10MB)
- 계획과 달라진 점: "계속 실패하는 공고 건너뛰기"는 실패 횟수를 저장할 칸(서버 구조 변경)이 필요해 이번 수정에서 뺌 (같은 문제가 다시 나오면 수정 명세로)
- 확인: Node로 옛·새 코드 비교 스크립트 실행 — 크기·색 종류 6가지와 데이터 모자람·모르는 필터에서 결과가 같음. 2,000만 픽셀 투명 PNG의 늘어난 최대 메모리 263MB → 41MB.
  `npm run build` 성공, `npm test` 39개 통과, `cargo check` 성공, imagePdf.ts tsc 엄격 타입 검사 통과. Deno가 없어 함수 실행 환경에서는 돌려 보지 않음.
- 사용자 확인: 대기 (서버 업데이트 뒤 [지금 평가], 출시 확인 C1)
- 남은 문제: 실제 공고 이미지의 픽셀 크기·투명 여부는 읽기 전용 연결로 볼 수 없어 서버 업데이트 뒤 로그로 확인해야 함
- 주요 파일: supabase/functions/js-process/imagePdf.ts, supabase/functions/js-process/batch.ts
